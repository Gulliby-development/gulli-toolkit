# Working on Gulli Toolkit

These instructions apply to every coding agent (Claude Code, GitHub Copilot, Codex and others) and to human contributors.

## Project

Gulli Toolkit is a set of our own small World of Warcraft addons for WoW Forever, in one repository. Each top-level `Gulli-<Name>` folder is one addon as it goes into `Interface/AddOns`: `Gulli-Toolkit` is the core (the hub), every other folder is a module (`Gulli-QuestCleaner`, `Gulli-Bulletin`, `Gulli-BagSpace`, ...).

- WoW Forever is Vanilla content on the Retail engine. The API is Retail's (`C_QuestLog`, `C_Container`, `C_Item`, `C_AddOns`); the quest and item data are Vanilla's. Keep a fallback to the old global API where it costs one line, so an addon also loads on a client without the `C_` namespaces.
- TOC: `## Interface: 16001`. The index and Runeloader treat `## Interface: 160xx` as a Forever build.
- Our own addons are all named `Gulli-<Name>` (G-U-L-L-I, after the nick Gulliby). The folder, the TOC and the title use that name; the module key is `<Name>`.
- Plain Lua 5.1 with no libraries (no Ace3, no LibStub). The whole UI is built in code.
- It ships through [Runeloader](https://github.com/Gulliby-development/runeloader): the [runeloader-index](https://github.com/Gulliby-development/runeloader-index) lists it from `seeds.txt` as one package, the core plus one entry per module.
- The repository is GPLv3 (QuestCleaner carries QuestieDB data).

## Modules and the core

- A module is a normal addon that works alone. It never needs the core. Its TOC has `## Interface: 16001`, `## Version: x.y.z`, `## OptionalDeps: Gulli-Toolkit` (so the core loads first), `## X-Gulli-Module: <Name>` (so the hub lists it even when it is switched off), `## IconTexture`, `## Category: Gulli` and `## X-License: GPL-3.0`. CI checks these lines.
- At file load a module registers with the hub: `do local register = GulliToolkit and GulliToolkit.Register or function(info) ns.alone = info end; register({ key = "<Name>", open = function() ... end, icon = ..., slash = "/g.." }) end`. Without the hub the table goes to `ns.alone`, and the module's `Skin.lua` gives it its own minimap button at `PLAYER_LOGIN` (`S.AloneButton`: always shown, since only the hub has the switch for it; a click opens, a drag moves it, its place in the module's first saved variable as `gulliMap`, the buttons of several modules alone take free places beside each other through `GulliHUD.alone` and `S.AloneAngle`). The toolkit test checks that every module registers this way. `title` and `desc` are optional; a known module shows the hub's own `M_<Name>`/`D_<Name>` texts, another one its `title`, then the TOC `Title` and `Notes`. A module's name in the game (the hub's `M_<Name>`, the module's `TITLE` on its window) has no `Gulli` prefix: only the folder, the TOC and the game's AddOns list say `Gulli-<Name>` (`ns.ShortName` strips it from other titles). `category` (a key of `ns.CATEGORIES`) is optional too: a known module has its group in `ns.CATEGORY_OF`, another one may name it in Register or in its TOC (`## X-Gulli-Category`), else it is `Other`. `options` is an optional list of the module's main switches (`{ label, get, set, icon, tip }`, `icon` and `tip` optional, at most six), with the same saved keys as its window; the hub's search finds a module by them. `summary` is an optional function that returns one short line (and optionally an icon path) for the hub's home page, such as "Level 24 in 1 h 10 min" or "2 entries left"; it must be cheap and safe to call at any time, and return nil when there is nothing to say. Its optional third value is a table for the module's tile (`ns.TileOf`): `tone` (`bad`, `warn`, `good`: only a state, as everywhere), `value` (the tile's big number when the line does not start with it), `label`, `pips = { have, of }`, `ready` (the key of the Ready check that shows the same, so the tile gives way to it) and `quiet = true` (nothing to do: the first tile to go). `session` is an optional function for the home page's session card (`ns.SessionOf`, `ns.SessionCard`): it returns `{ value, unit, line, span, bars, progress = { value, extra, left, right }, at, tile = { icon, value, label }, facts, tip = { icon, head, value, rows } }` or nil when it has nothing to show (Gulli XP: the pace while levelling; Instance Limit: the runs since the login; Farm Tracker: only a `tile`). `value` makes it a source that can lead the card, `at` is when it last gained (`time()`), `tile` is its small tile while another source leads, `facts` are short texts for the card's quiet line and `tip` its part of the card's tooltip; `worth` (copper, alone enough for a table) is what the items the session looted would bring, which the card adds to its gold; it must be cheap and safe to call at any time. A new source of the card is a module that gives `session`, with a place in `ns.SESSION_FIRST` (who leads) and `ns.SESSION_TILES` (the order of the tiles); only what every character has and no module owns (honor, gold) is counted by the core itself. `move(on)` shows (true) or ends the module's frames with their movers for the hub's Unlock mode; `frames` lists those frames for the Unlock panel (`{ key, label, icon, get, set, frame }`: `get`/`set` are its show switch, left out for a frame that shows by itself such as a notice card, `frame()` returns the frame with its `S.Mover`, built when it is asked for, so the first Unlock already places it; the hub's `FR_<Name>` text names it); `reset()` puts the module's settings back to their defaults for the hub's **Reset to defaults** (it must refresh the module's window and frames). `pause(on)` stops (true) or starts (false) the module at once, so the hub's switch needs no reload: the module sets `ns.paused`, its event handler returns early for every event but the `_CLOSED` ones, its hooks check `ns.paused`, and its own frames (panels, vendor buttons) hide; the hub keeps the pause in `GulliToolkitDB.paused` and calls `pause(true)` again when the module registers after a reload. A module that acts on its own gives `pause`, with a test that a paused module does nothing. `window` gives the hub the module's main window so it can show it inside `/gulli`: `window = function() return ns.Window and ns.Window() end`, where `UI.lua` has `ns.Window()` (builds the `S.Window` once and returns it) and `ns.Toggle()` calls `S.ToggleWindow(ns.Window())`, so the slash command takes a window out of the hub instead of closing it. Work that `ns.Toggle` does when the window opens also runs from an `OnShow` hook when `self.docked`, because the hub shows the window itself. A module with several windows gives its settings window (Mail's mailbox panel stays at the mailbox). `Register` accepts `.` and `:` calls. `tweaks` lends the hub's **Tweaks** page some of the module's own switches as rows (`{ key, group, label, desc, icon, tip, get, set, shift }`, `group` a key of `ns.TWEAK_GROUPS`, `shift` when it acts for the player so Shift skips it once; the same saved keys as its window; a row whose module is off or paused shows dim with a way to the module, and Recommended and Turn all off never touch it). A new field in this table is optional for the core; the core keeps `GulliToolkit.api` and raises it on a breaking change.
- The core offers two services a module may use, always behind a check that the core is loaded (`if GulliToolkit and GulliToolkit.IsProtected then ... end`):
  - `GulliToolkit.IsProtected(itemID)`: items the player protected in the hub. A module that sells, deletes, moves or offers bag items skips them (QuestCleaner, BagSpace). A new module that removes items checks it too, with a test.
  - `GulliToolkit.Notify(key, text)`: one line in the hub's **Recent** feed (newest first, `FEED_MAX` lines). Use it for news the player may miss in chat (a limit reached, a cooldown ready), not for every event.
- Each module has its own copy of `Skin.lua` and of its round shapes in `Media/` (same look, no shared code at run time). The copies in `Gulli-Toolkit/` are the originals: change only those, then run `tools/skin/sync.sh` to copy them into every module. CI fails when a copy differs. `tools/skin/media.py` draws the `Media/*.tga` files (`Round`, `RoundSq`, `Glow`, `Ring<R>`); a new corner radius gets a ring there and in `RADII` in `Skin.lua`.
- A new module gets: its icon from the Codex template in `docs/toolkit/PROMPTS.md` (a row in its table; `docs/<name>/icon.png` 256 px and `Gulli-<Name>/icon.tga` 64 px; never a hand-drawn stand-in), its folder `Gulli-<Name>/`, its tests in `tests/<name>/` (lowercase, its own fake client `wow.lua`), its player page `docs/<name>/README.md` with its images, a row in the module table of `README.md`, its key in `ns.KNOWN` in `Gulli-Toolkit/Core.lua` with `M_<Name>` and `D_<Name>` in every language of `Gulli-Toolkit/Locales.lua`, and its tag group in [Releases](#releases).

### Gulli-Toolkit (the core)

- `Gulli-Toolkit.toc` loads `Locales.lua`, `Core.lua`, `Tweaks.lua`, the own tweaks `Tweaks\<Name>.lua`, `Setup.lua`, `Ready.lua`, `Session.lua`, `Skin.lua`, `UI.lua`, `TweaksUI.lua`. It keeps `GulliToolkitCharDB` per character (`session`: what `Session.lua` counted since the login) and `GulliToolkitDB` account-wide (`setup`: the first setup was done, `protected`: item id -> true, `feed`: the Recent lines, `scale`: the hub's size, `minimap`: `hide` and `angle` of the minimap button, `pins`: module key -> the angle of that module's own minimap button, or false when the player turned it off, `pinRings`: module key -> 2 for a button on the second ring, `last`: the module the hub opens on, `seen`: module key -> version last opened, `errors`: the errors of the Gulli addons, newest first, at most `ns.ERRORS_MAX`, `calm`: Reduce motion, set by `ns.SetCalm` from the switch on the Setup page and the Options page, `ready`: the limits and switches of the Ready card, defaults in `ns.READY_DEFAULTS`, `unlock`: the Unlock mode's `snap` and `step`, `toastAt`: where the notices stack, `sideTab`: the tab chosen last beside the auction house, written by the skin's side tabs).
- `Setup.lua` holds the first-run window's rules: when `GulliToolkitDB` does not exist yet (`ns.firstRun`), `PLAYER_ENTERING_WORLD` opens `ns.OpenSetup` once (also **First setup** on the Setup page and `/gulli setup`). `ns.SetupPlan` gives each installed module a start value and a grey reason from `ns.OTHERS` (popular addons by folder name: `same` = it does the module's job, the module starts off, "Because you have X"; `with` = the module uses it, it stays on; a list of keys instead of `true` counts only those saved settings of the addon, `db` its saved variable) and `ns.CLASS_OFF`; anything else keeps the game's state. `ns.ApplySetup` switches through `ns.Switch` (each in a `pcall`, the modules the game did not take named in one line) and sets `setup`; closing the window sets it too. When the picks need a reload, the window stays and its button turns into **Reload now**: `ReloadUI` always runs in a click of its own, never in the click that switches (the game refused it there). A new overlap goes into `ns.OTHERS` with the folder name read from the addon's TOC (never guessed from a CurseForge page) and a case in the toolkit test; the test checks every key is a known module.
- `Session.lua` holds the session of the home page. It counts by itself, since the player came into the game (`ns.SesEvent`; the session rule of Working conventions, `S.NewSession`): honor (`ns.SesHonor`: the honor currency, the honor bar and the chat line all tell of one gain, so the first of them that reports is the session's source, `honorSrc`, and the others are ignored; a new way to read honor is one more source there, with a case in the test), the gold earned (`ns.SesMoney`: loot, quest rewards and vendor sales, less repairs, `ns.SesRepairCheck`; nothing at the mailbox, the auction house, the bank or in a trade, and a spend that is no repair is not counted; when a module's `session` gives `worth`, the card's gold is an estimate: loot and quest gold plus that worth, less repairs, and the vendor sales step back since what was sold is in the worth already, with a case in the toolkit test), kills (XP messages, so only while levelling), quests handed in, deaths and the best loot (rare or better). It only reads the game; an amount that is a secret value is left alone. `ns.SessionCard` puts the card together from the core's own sources (`ns.SESSION_OWN`) and the modules' `session`: the leader is the first of `ns.SESSION_FIRST` that gained in the last `ns.SES_RECENT` seconds, else the first with a number; the other sources give at most `ns.SES_STATS` tiles in the order of `ns.SESSION_TILES`, free places take the small counters (kills, quests, deaths), what found no tile is a fact of the quiet line, and every source gives a group of the tooltip. Counts are shown as `Label: number` (`SES_FACT`), never as a counted noun, so no language needs plural forms. A new counter of the core gets its event in `ns.SesEvent`, a `SES_` text in every language and a case in the toolkit test.
- `Ready.lua` holds the readiness checks for a trip or a dungeon (`ns.Readiness`: repairs, free bag slots, food and drink apart by the item's Drink spell, the hearthstone, hunter ammo, the class reagent or shards from `ns.READY_CLASS_ITEMS`, and what Gulli Restock's list misses through `GulliRestock.Missing`), each against a limit read through `ns.ReadyGet`. The home page shows them as the **Ready** card: a ring with a run of marks per check (`ns.RingTicks`, the marks are `Art/Arc` turned around the centre) and a bar per check with a mark at the player's limit (`frac` and `mark` of the check; `ns.ReadyBar` for a count against its limit); its **Settings** opens a centre page (`ns.BuildReady`). A new check gets a key in `ns.Readiness` with its `frac`, an icon in `ns.READY_ICON`, an `RD_` text and a short `RD_L_<KEY>` name in every language and a case in the toolkit test.
- `Core.lua` holds the global `GulliToolkit` (`modules`, `Register`, `Open`, `api`), the list of known modules (`ns.KNOWN`), the hub rows (`ns.List`: only installed modules, the known ones first, then any other `X-Gulli-Module`, each `ready`, `off`, `reload` or `blocked` (enabled, but the game refuses to load it; `reason` is the game's `IsAddOnLoadable` reason, shown through `ns.ReasonText`); a module that is not installed has no row and shows up once installed (owner's decision)), the switch (`ns.Switch`: a running module with `pause` pauses or starts at once, `row.paused`; any other goes through the game's list; `ns.SetLoaded` is the card's **Do not load in the game** / **Load in the game**), switching a module on or off in the game's AddOns list (`ns.SetEnabled`: for this character, named both by GUID and by name since clients differ, and for every character, then `SaveAddOns`; the state read is the lowest answer of the forms, and `/gulli debug <module>` prints the raw answers; it takes effect after a reload and reports when the game did not take it; there is one state, the game's: `row.on` is always read from the game (enable state and `IsAddOnLoadable`), never kept by the hub, and a row whose switch and what runs disagree is `reload`, see `ns.NeedsReload`), the protected items (`Protect`, `IsProtected`, `ns.Protected`), the feed (`Notify`, `ns.Feed`) and `/gulli` (`/gulli <module>` opens a module, `/gulli protect <item link>` protects or frees an item).
- `UI.lua` is the hub window (owner's decision): on the left a narrow list of the modules without switches (icon and name; the name's colour shows `reload`, `blocked`, off or paused (grey), a dot on the icon marks `row.new`), grouped by `ns.Groups` with `on/total`, the search on top (it also finds a module by its `options` labels and `tip`s; Enter opens the first). The one switch is in the header of the module's page (owner's decision). In the centre always one page: a click on a module docks its window there at once (`enter`, `ns.Enter` for the tests; `f:Dock` with **<** back to home, the on/off switch in its header). A narrow window keeps the module card beside it (icon, group, state, description, command, version, memory, **Reset to defaults** when the module gives `reset`, **Reload** when it waits for one, **Do not load in the game** for a module with `pause`, **Open in its own window**); a wide one takes the whole centre. A module that is off, waits for a reload or is refused shows a page that says so; a module without `window`, or with a window bigger than the centre, opens alone as before. With nothing chosen the centre is the home page, a dashboard with few words (owner's decision): on top the **Ready** card and the session card side by side (`ns.SessionCard`: the leading number big with a column per stretch of time beside it, its line, the small tiles, the quiet line of as many facts as fit, the level's bar while levelling, the whole list in its tooltip; a click opens the module that leads; a session with nothing in it yet says what will come, so the card always shows and takes the whole row when the Ready card is off); under them the `summary` of every module that runs (also one waiting for a reload) as number tiles (`ns.Tiles`: `ns.TileOf` takes the number a line starts with as the big one, bad then warn first, quiet last, at most `ns.TILES_MAX`; a tile gives way to the Ready check and the session card that show the same; a long line takes two lines; a click opens the module); at the bottom the **Recent** feed (`ns.FeedRows`: the module's icon, lines of one module in a row joined as `x3`, `ns.Ago` at the right; a click opens the module, **Clear**) and the **Modules** card from `ns.Overview` (on/total, memory, a pip per module, the heaviest by memory as bars, **Reload** when a module waits for one, and lines only for what the player should know: errors, modules that wait for a reload, that the game refuses, that are paused or were updated; a click opens the first named). Nothing on the home page is a setting. **Unlock frames** is a link at the right of the window's header on every page (`ns.SetMoving`, with the frames that show counted beside it). The **Setup** page (the row under Home, `ns.OpenSetupPage`) holds what the player sets once, on the window's own background with no box around it: at the right of its title how many modules are on and, only while a switch waits for one, the reload as a button of its own; the presets of `ns.PRESETS` as cards (icon, name, the installed modules of the preset as small icons, **Apply** through `ns.ApplyPreset`); the **Modules** board, a line per group of `ns.Groups` with every installed module as a round icon that a click switches through `ns.Switch` (a dot shows the state: green on, hollow grey off, yellow waits for a reload, red refused; its tooltip names it); the **This window** card (the **Reduce motion** switch and the window size); the **Minimap buttons** card (`fillPins`: the hub's own button first, then every installed module as a round icon, bright with a gold dot when its button is at the minimap; a click puts it there or takes it away); and the tools as tiles (**Export / import**, **Protected items** with their number, **First setup**); a page opened from it goes back to it. A new tool is a tile there with a `TOOL_` text in every language; a new state of a module gets its dot on the board and a case in the toolkit test. A new kind of line on the Modules card goes into `ns.Overview` with an `OV_` text and a case in the toolkit test. Protected items and Export / import are pages in the centre too. The hub opens on the module that was open last (`GulliToolkitDB.last`, cleared by **<** and Home). The window is `S.NARROW_W` + the card wide and `S.DOCK_H` + the header high (1086 by 700), and `ns.HubScale` shrinks it to fit the screen times the player's window size from the Setup page (`GulliToolkitDB.scale`). It also adds the page under Options, AddOns, and the one minimap button (`ns.BuildMinimap`: a click opens the hub, a right-click starts the Unlock mode at once and the next one saves it (`ns.MinimapClick`), a drag moves it around the minimap; `ns.MinimapOffset` places it on a round or square minimap; the **Minimap button** switch on the Setup page and on the Options page, and `/gulli minimap`, hide it). A module has a minimap button of its own when the player pins it, and a module of `ns.PIN_DEFAULT` (the ones with their own CurseForge project) shows it until the player turns it off (owner's decision of 2026-11-20; `GulliToolkitDB.pins[key]` is an angle, `false` when the player took it away, nil when nobody switched it): the **Minimap** switch in the header of every module's page beside its on/off switch, or its icon on the Setup page's **Minimap buttons** card (`ns.SetPinned`, `GulliToolkitDB.pins`). The hub draws these buttons, a module never makes one itself: `ns.Pins` gives the pinned modules that run (one that is off, paused or waits for a reload keeps its pin and gets the button back), `ns.PlacePins` shows them, a new one takes the first free place beside the hub's button (`ns.FreeAngle`), and when that ring is full the second ring farther out (`pinRings`, `S.MapRadius`); the buttons are `S.MapButton` of `Skin.lua`, the same as a module alone draws, a click calls the module's `open`, a drag moves it, and its tooltip (`ns.PinTip`) has the module's `summary` line. A change to these rules gets a case in the toolkit test. It only shows what `Core.lua` holds.
- `Tweaks.lua` holds the rules of the **Tweaks** page (the row under Home, before Setup; `/gulli tweaks`, `ns.OpenTweaks`), `TweaksUI.lua` only shows them (`ns.BuildTweaksPage`, `ns.FillTweaks`). Two kinds of rows: the toolkit's own tweaks and the rows the modules lend through `tweaks` in Register. An own tweak is a file of its own, `Gulli-Toolkit/Tweaks/<Name>.lua`, with its line in the TOC, added through `ns.AddTweak{ key, group, icon, star, shift, defaults, panel, enable(get), disable(), changed(opt, value, get) }`, a place in `ns.TWEAK_ORDER`, the texts `TW_<KEY>`, `TW_<KEY>_D` (one line) and optionally `TW_<KEY>_T` in every language, and a case in the toolkit test. It keeps `GulliToolkitDB.tweaks[key]` (`on` and its options, read through `ns.TweakGet`, defaults in `defaults`); every tweak starts at `PLAYER_LOGIN` and starts and stops in a `pcall` (`ns.StartTweak`, `ns.StopTweak`, an error goes to the error log), so one broken tweak never stops the others. `disable` undoes everything `enable` did (hooks go quiet, a CVar gets the player's value back). A tweak that acts for the player (accepts, skips, declines) has `shift` and checks `ns.TweakSkip()`. Its `panel` lists the parts under its row: `head`, `switch` (behaviours that are on or off on their own), `check` (picks entries of a list), `choice` (`S.Tabs`) and `step` (`S.Stepper`), each optionally with `when(get)`. `star` puts it in **Recommended**; Recommended and **Turn all off** change only own tweaks and offer Undo (`ns.TweaksRestore`). The groups are `ns.TWEAK_GROUPS` with an icon in `ns.TWEAK_GROUP_ICON` and a `TWG_<KEY>` text; the filter track shrinks to fit (names without group icons, then icons only), and an eighth group needs a wrap or an overflow menu first. The hub's search finds tweaks too (a **Tweaks** row on top of the list). A tweak that changes a game setting (CVar) goes through `ns.TweakCVar(owner, cvar, value)` of `Tweaks/CVars.lua` and gives it back with `ns.TweakCVarsRestore(owner)` in `disable`: the player's own value is kept in `GulliToolkitDB.tweakCVars`, a setting the client lacks (`ns.HasCVar`) is never touched and its panel part hides (`when`), and a setting the player changed since stays; a row only for a setting some clients lack (Cooldown numbers) is added only when `ns.HasCVar` says it is there. The combat, interface and sound tweaks: **Consumable macros** (`Tweaks/Macros.lua`: `ns.MACROS` and its item lists `{ id, level }`, the highest level the character may use wins, per-character macros named `TWM_<KEY>` (at most 16 bytes in every language), changed only out of combat; a new macro gets an entry, `TWP_MAC_<KEY>` and `TWM_<KEY>` texts and a case in the toolkit test), **Swing timer style** (`SwingStyle.lua`: only restyles the game's own `Blizzard_SwingTimer` bars, never shows, hides or moves them), **Error message filter** (`ErrorFilter.lua`: `ns.ERROR_KINDS` by `LE_GAME_ERR_<name>`, hidden through `UIErrorsFrame:SetMessageTypeEnabled` and given back as the game had them; a new kind gets an entry, a `TWP_ERR_<KEY>` text and a case in the test), **Right-click guild invite** (`GuildInvite.lua`: writes `/ginvite` into the chat box, never invites itself), **Hidden game settings** (`GameSettings.lua`: `ns.GAME_SETTINGS`, one switch per CVar; a new one gets an entry, a `TWP_GS_<KEY>` text and a case in the test), **Cooldown numbers** (`CdNumbers.lua`) and **Quieter game** (`MuteSounds.lua`: `ns.MUTE_SOUNDS` is written by `tools/tweaks/build_sounds.py` from the game's file list; a new kind of sound is a row in its `KINDS`, a key in `ns.MUTE_KINDS`, a `TWP_MUTE_<KEY>` text and a case in the test).
- More in `Core.lua`: `GulliToolkitDB.seen` (module key -> the version the player last opened; a module whose TOC version differs is `new`, the first version seen is only noted), `ns.Export`/`ns.Import` (every saved variable named in the TOCs, `GULLI1:` and a plain serializer, `ns.Deserialize` reads only what `ns.Serialize` writes and never runs the text; import sets only `Gulli...DB` globals and asks for a reload), the version check in the group (prefix `GulliTK`, `V|Core=1.6.0|XP=1.4.0`, at most 240 characters a message, at most once a minute; a newer version is told once per session; add a new message type, never change this one), the error log (`ns.HookErrors` chains to the error handler that was set before and keeps a copy of every error whose message or stack names a `Gulli-<Name>/*.lua` file, `ADDON_ACTION_BLOCKED`/`FORBIDDEN` for a Gulli addon too, through `ns.RecordError`; a repeat counts up and moves to the top; `ns.ErrorsText` is the text for a bug report, `/gulli errors` and the **Errors** line of the Modules card open its page; it never stops or hides an error), `ns.ItemName` (an item's name once the client has it, kept for the session; until then the page shows `...`, the game is asked for it and `GET_ITEM_INFO_RECEIVED` redraws the hub through `ns.OnItemInfo`; a page of the hub never shows `item:<id>`), `ns.Memory` and `/gulli help` (`ns.HelpLines`: the toolkit's commands, then every ready module's `slash`).
- A new preset goes into `ns.PRESETS` (known module keys only) with an `icon` and a `PRESET_<Key>` text in every language; the test checks them. The other buttons of the Setup page take their icons from `QUICK_ICON` in `UI.lua`.
- A new module group gets a key in `ns.CATEGORIES`, a `CAT_<Key>` text in every language and a case in `tests/toolkit/test.lua`.
- The game's addon calls go through the wrappers at the top of `Core.lua`, with a fake in `tests/toolkit/wow.lua`.

### Gulli-QuestCleaner

- `Gulli-QuestCleaner.toc` loads `Locales.lua`, `Data.lua`, `Core.lua`, `Skin.lua`, `UI.lua` in this order. It keeps `GulliQuestCleanerDB` account-wide (`quests`, `items`, `offerFailed`, `zoneOnly`, `keep` (item ids), `keepQuests` (quest id -> title, quests the player unticked), `keepComplete`, `keepClass`, `keepDungeon`, `keepElite`, `keepGroup` (unset follows `keepElite`), `tooltip`, `key`; `level` only as the start value for older saves) and `GulliQuestCleanerCharDB` per character (`level`, `last`). The tests load the files in the TOC order.
- `Data.lua` is generated by `tools/questcleaner/build_data.py` from the QuestieDB Forever data; never edit it by hand. `ns.Data` has `need` (quest item -> quests that ask for it), `quest` (quest -> level, race mask, class mask, max level, quests that close it), `keep` (quest-class rewards no quest asks for), `itemStart`, `chain` and `class` (quest id sets), `start` (quest -> giver: an NPC id, or minus an object id) and `giver` (giver -> name, area id) for `ns.WhereToTake`. Race masks pass 2^32 on Forever: test bits with arithmetic, not `bit.band`. Because of this data the addon is GPLv3.
- `Locales.lua` has the texts of every language: `ns.L` reads the game client's language and falls back to English.
- `Core.lua` holds the rules and touches the game: the quest log scan (`ns.Quests`), the plan (`ns.PlanQuests`, `ns.PlanItems`, `ns.ItemGoes`), the run (`ns.Run`, `ns.Leftover`), the slash commands and the saved variables.
  - A quest is planned when its level is at or below the entered level (or the gray level, `ns.GrayLevel`, or the green level, `ns.GreenLevel`), and in the zone when one is given. Headers, hidden quests and quests without a level stay, and so do locked quests, finished quests, class, dungeon/raid, elite and group quests while their switch is on (`protectedBy`). A failed quest is planned at any level (`offerFailed`). A quest that an item started is planned unticked (`warn = "TAG_ITEM"`); a chain quest is marked (`TAG_CHAIN`).
  - Each quest keeps its zone: the quest log header above it. `ns.PlanQuests` sorts by zone in quest log order, then by level; `ns.Zones` groups the plan by zone for the window.
  - A bag item is a quest item when its class is Quest (12), the game marks it as a quest item, or it starts a quest. While the bank is open, its containers count too (`ns.BankBags`); a bank item is deleted, never sold.
  - `ns.ItemVerdict` gives the tooltip line of a quest item (kept, needed for a quest in the log, needed later, offered) from the same rules, cached until the quest log or the bags change; `ns.TipLines` makes it a line of the Gulli block.
  - A quest item is offered when no quest that stays in the log needs it. "Needs" means its name is in the quest's objectives, summary or description, or it is the quest's usable item. The planned quests that need it become its `links`; an item with no link is listed under "No quest".
  - The data adds to this: a quest in the log that the data lists for the item keeps it or links it like the text does. An item the data lists for a quest above the entered level that the character can still take (`canTake`) is not offered; `ns.PlanItems` returns those items as its second value. The data only ever adds reasons to keep an item.
  - An item that starts a quest is offered only when that quest is already done.
  - `PERMANENT` lists quest items that stay useful after their quest (dungeon keys, attunements, raid summoning items), and `Data.keep` adds the quest-class rewards no quest asks for. They are never offered. Items the player unticked go into `keep` and are not offered again until `/gqc reset`.
  - `ns.ItemGoes`: an item goes only when it is ticked and every quest it is linked to goes too.
- `Skin.lua` is the Gulli Hearth look: dense dark-brown rounded panels, gold names, a blue accent (`S.Accent`, `S.FILL`), round icons in a thin dark gold ring, pill switches, flat buttons, check boxes, edit boxes and a thin scroll bar, all drawn from plain textures and the shapes in `Media/`.
- `UI.lua` is the window: the setup view (level with a **Gray** button, what to clean, the three protection switches) and the preview (zones with their quests on the left, items on the right, a line from each quest to its items; a zone row ticks or unticks all its quests; below, the quest log and bag places before and after **OK**). It shows what `Core.lua` planned and never decides on its own what to remove.
- With a merchant open (`MERCHANT_SHOW`), `ns.Run` sells an item that has a price instead of deleting it. It saves what it removed in `last` for `/gqc last`. When the log is two quests from full, `QUEST_ACCEPTED` prints one chat hint; it never removes anything.
- Removing things runs inside the **OK** click, because the game lets an addon delete a picked-up item only inside a hardware event. The game confirms a delete later, so `DeleteCursorItem` is restricted: the game allows one call per hardware event and blocks the next one (`ADDON_ACTION_BLOCKED`), so one **OK** abandons every ticked quest and sells, but deletes only one item (an item tried before goes last, `it.tried`, so a refused one never holds up the rest; `ns.ToDelete` counts the clicks left). The game confirms a delete later, so the cursor can still hold the item right after `DeleteCursorItem`: `ns.Run` clears it and goes on. A moment later `ns.Leftover` shows what is left, and the player presses **OK** again for the next item. The same holds for every module that deletes items (BagSpace); the fake clients block a second delete per click (`W.Click()` is a new click).

### Gulli-GroupBuffs

- `Gulli-GroupBuffs.toc` loads `Locales.lua`, `Buffs.lua`, `Core.lua`, `Skin.lua`, `UI.lua`. - `Buffs.lua` lists the buffs per class by rank 1 spell id (a pick-one family names its list in `B.CHOICES` and its start value in `B.CHOICE_DEFAULT`) (`who`: `all`, `mana`, `self`, `thorns`, `blessing`; `group`: the party-wide spell; `anyOf`: a pick-one family whose members are one at a time by the player's choice of the moment (paladin auras, shields), so any one of them that is on counts; `race`: a racial buff, listed in the window only for that race or when known; `ranks`: higher rank ids, used when the client does not know rank 1). - `Core.lua` holds the rules and reads the game; it never casts. `ns.Plan` returns the missing buffs in casting order (you first, then the group in roster order, then a friendly target) and, as a second value, the ones out of range. A group spell replaces the single casts of one party when `groupMin` of it need the buff and the spell is usable (has its reagent). A Greater Blessing (the first `also` id in `B.BLESSINGS`) replaces the single blessings of one class across the group the same way, only while every member of that class gets the same blessing (no role rule gives one of them another). A hidden aura (a secret name) is skipped one by one, and a watched buff that did not show is asked for by name (`C_UnitAuras.GetAuraDataBySpellName`); a unit is left alone, never nagged, when the game cannot tell (in a fight a miss by name proves nothing, so only a found buff counts there). In combat a press the game confirmed (`UNIT_SPELLCAST_SUCCEEDED` after `noteCast`) marks that unit and spell done by GUID (`landed`, cleared when the fight ends), so the bar greys it and says when the whole list is done; combat entries keep the GUID and name they had when the fight began. A stat buff is not missing when the unit's Camp Benefits aura (`ns.CAMP_SPELL`, read from its tooltip by `ns.CampStats`) gives as much of that stat (`ns.STAT_BUFFS`: rank 1 id -> stat and amount per rank; a new stat buff gets its ranks there), and a buff the game refused as weaker (`SPELL_FAILED_AURA_BOUNCED`) is left alone on that unit while the camp lasts or ten minutes (`ns.Bounced`). Both are per unit (the camp read from that unit's own aura, the refusal kept by GUID): your camp never covers anyone else. Every game answer about another unit goes through `ns.Ask` (pcall, and nil for a secret value), and `ns.Plan` checks each unit in its own `pcall`: in a dungeon the game may hide or refuse an answer for one member, and that leaves only that member out (`ST_HIDDEN`), never the whole bar. Reminders has the same rules for its own buffs and the ones it asks others for. With `thank` (off by default, owner's decision of 2026-11-21) a friendly player outside the party and raid whose buff lands on you (`ns.NoteBuffs` reads `sourceUnit` of the player's `UNIT_AURA` added auras, out of combat) is noted by GUID for `ns.THANK_SECONDS`; `ns.AddThanked` adds them to `ns.Units` while a token finds them (`ns.TokenOf`: target, focus, mouseover, name plates), they get one buff (`thanks`), `ns.CombatList` leaves them out, and our cast that lands on them (`ns.Thanked`) or their joining the group ends it. A member of the group is never thanked. Pets follow their owner (`who = "all"`, and `mana` when they have mana); a unit whose cast just failed is skipped for `ns.SKIP_SECONDS` (`ns.Skip`). `ns.Status` gives why nothing is cast (also how many units the game hides buffs on, `ST_HIDDEN`, and how many already have something stronger, `ST_STRONGER`); a new reason gets an `ST_` text in every language and a test. The marks on the game's party and raid frames, and on other addons' frames whose `unit` attribute is a party or raid unit (`ns.ScanFrames`, every 15 seconds out of combat and a second after a roster change), are textures of our own, kept in a weak table, never fields on those frames.
- `UI.lua` holds the secure buttons: `GulliGroupBuffsButton` (the big one, also on the key through `SetOverrideBindingClick`) and its small buttons. Their attributes change only out of combat. On `PLAYER_REGEN_DISABLED` the plan goes into `gb-spell<i>`/`gb-unit<i>`/`gb-count` of the big button, and `ns.COMBAT_SNIPPET`, wrapped on its `OnClick`, aims it at the next living unit of that list on each press, wrapping at the end; within `ns.HOLD` (a global cooldown) of the last aim it stays on that unit (`gb-held`, `gb-at`, read with `GetTime` when the environment has it), so spammed presses do not walk past people nobody buffed. The snippet may use only what the restricted environment has (`PlayerInCombat`, `SecureCmdOptionParse`, the frame handle); the test runs it with only those. In combat the insecure code changes only textures and texts. A buff of your own that falls off in a fight and is not on that list (`ns.SelfFaded`, only when the game shows your auras, gone and not just low) gets one `S.Toast` and a caption line per fight (`ns.CheckFaded` on `UNIT_AURA` for the player, behind `fadeAlert`), since the key cannot be aimed at it until the fight ends.

## Task workflow

- Track planned work as GitHub Issues in this repository, not in Markdown files or TODO comments. Before you start, find the issue for the task or open one. Record a new idea, a follow-up or a deferred item as an issue.
  - Issue types: Task, Bug or Feature.
  - Labels: `idea` (not decided yet), `deferred` (agreed for later), `needs-owner` (only the owner can do or decide it), `verification` (needs the real game), and `area:core|quests|items|ui|locales|build|ci`, and `module:<name>` for the module it is about.
  - Put `Priority: P0|P1|P2` on the first line of the issue body. P0 blocks current work or a release, P1 is next, P2 is later or an idea.
- Before you open or extend a Bug issue, follow the [file-issue skill](.agents/skills/file-issue/SKILL.md). It finds the root cause and sweeps the code for every other place with the same defect. A pull request that fixes such an issue fixes every place the issue lists and reports the result in a `## Sweep` section of its description.
- Every Feature and Task issue has a `## Maintainability` section. It names the rule a later change must follow when the task adds something that later code must extend (a new module, a new item rule, a new language, a new saved setting). It says `None` when nothing needs extending. The pull request that adds such a mechanism adds its rule to this file.
- Start every task on its own branch from an up-to-date `main`:
  - new feature, documentation, CI or refactor: `feature/<name>`;
  - bug fix: `bugfix/<name>`.

  `<name>` is a few lowercase words joined by hyphens. Do not use other prefixes (`docs/`, `fix/`, `claude/`, `copilot/`) or generic names such as `patch` or `update`. If your tool proposes a default branch, rename it before the first push. CI fails a pull request whose branch breaks this rule; only Dependabot's `dependabot/` branches are exempt.
- Commit working states on the task branch. Before each commit, run the tests of every module you touched (`lua5.1 tests/<name>/test.lua`), so every commit passes.
- A pull request that finishes an issue says `Closes #N` in its description. Use `Refs #N` when the pull request does only part of it.
- Before you finish a task, check `README.md` and the module's `docs/<name>/README.md` against your change and update it in the same pull request: features, commands, button names, FAQ answers and images must match the addon as it is after the merge. Say in the pull request description that you checked it, or what you changed.
- When the task is complete and [Verification](#verification) passes, open a pull request to `main`. `main` takes changes only through pull requests with green CI. Do not push to `main` directly.

## Working conventions

- Keep the addon free of libraries. Use the game's API and Lua 5.1 only. A new dependency needs an issue and the owner's decision first.
- Register only events the retail client has (check the name in Blizzard's `Blizzard_APIDocumentationGenerated`; CI does it with `tools/apicheck/check.py` against the WoW Forever client in wow-ui-source (its `forever` branch, not `live`, which is the retail client), see [Verification](#verification)); a classic-only fallback event (`TRADE_SKILL_UPDATE`, `AUCTION_ITEM_LIST_UPDATE`) goes through a safe register like CraftProfit's `ns.Listen` (`C_EventUtils.IsEventValid`, then `pcall`), because one unknown name raises an error and stops the rest of the list. The same for game functions: a classic-only one (`GetMerchantItemInfo`, `GetItemInfo`, `UnitBuff`, ...) runs only behind its retail `C_` call, with a fallback check (`elseif GetMerchantItemInfo then`), and the module's fake client offers only the retail call, so a test catches a missing fallback.
- In combat the game can hand back secret values (`UnitHealth`, `UnitPower` and their max, `UnitLevel` of another unit, names, auras): check `issecretvalue` before any arithmetic, comparison or string work on them, and show nothing instead, with a test that feeds a secret value. A secret value can never be a table key: a key made from another unit's `UnitGUID` or `UnitName` is nil when either is secret. CI (`tools/ci/secret_units.lua`) fails on a `UnitName`, `UnitGUID` or `GetUnitName` of a unit other than `"player"` with no `issecretvalue`, `secret(`, `readable(`, `ask(` or `pcall` on its line or the lines around it.
- The game API goes through the small wrappers in the module's `Core.lua` (QuestCleaner: `slotInfo`, `numSlots`, `questInfo`, `pickup`, ...), which pick the `C_` function and fall back to the old global. A new game call gets such a wrapper and a fake in the module's `tests/<module>/wow.lua`.
- A key the player sets (a wheel key, a target key, a disenchant key) is saved through `S.KeyBase(key)` (its US name: `Ъ` becomes `]`) and bound through `S.BindKey(owner, priority, key, button, mouse)`, never with `SetOverrideBindingClick` directly: the game names a key by the letter the keyboard layout gives it, so `S.BindKey` binds every name of the same physical key (`S.KeyVariants`, the Cyrillic letters of `LAYOUT_KEYS` in `Skin.lua`; a new layout goes there, with a case in the toolkit test).
- Auction prices come only through `S.AuctionPrice(id, fresh)` of `Skin.lua` (price in copper and age in days, the first fresh one of `S.PRICE_SOURCES`: Auctionator `API.v1`, `AuxForeverAPI`, `NaowhForever.AuctionPrice`, `TSM_API`, `Hammerprice.GetPrice`, each through its public calls in a `pcall`), never from one addon's API directly; `S.HasPrices` says whether any is loaded. Without one, a setting that needs prices shows off and grey and keeps the player's saved choice for when one is installed (CraftProfit's auction switches and steppers, `AH_SWITCH`/`AH_STEP` in its `UI.lua`, and their hub `options`; Tooltip's `auction` line); CraftProfit then plans no profit route (`state.noPrices`) and shows a banner. A new setting that needs prices does the same, with a test. Only what one addon alone offers (Auctionator's shopping lists and scan times) calls it directly. A new price addon is a row in `S.PRICE_SOURCES` and its folder in the OptionalDeps of the modules that read prices (CraftProfit, Crates, FarmTrack, Tooltip, BagSpace, Mail), with a case in the CraftProfit test.
- A key per character is `Name-Realm`, and some WoW Forever sessions give an empty realm name (`GetRealmName()` is `""`). A module that saves per character takes the realm the game gives, else the one realm it saved for that name, else the last one it saw (`ns.Realm`/`ns.CharKey` in Attune, Chores and Legacy, `realm()` in Mail, `charKey` in Crates and Vendor Flip), and merges an entry saved as `Name-` into the realm one on load (`ns.MergeRealmless`). A reader of another module's characters (Tooltip and CraftProfit read Chores) skips `Name-` and the realm Chores saved last (`GulliChoresDB.realm`). Never fall back to `GetNormalizedRealmName()`: it drops the spaces, so its key differs from the saved one. A new per-character save does the same, with a test that feeds an empty realm name.
- A session (XP, the hub's session card, Farm Tracker, Fishing, Instance Limit's runs, Auto Quest's counters, Bulletin's board) lasts until the player leaves the game (owner's request of 2026-11-22): it is saved in the module's saved variables, a `/reload`, a loading screen and a dungeon keep it, and only `S.NewSession(isInitialLogin, isReloadingUi, seen)` of `Skin.lua` at `PLAYER_ENTERING_WORLD` starts a new one: a real login more than `S.RELOG_KEEP` (15 minutes) after `seen`, the time the module saved at `PLAYER_LOGOUT`, so a disconnect or a quick relog keeps it too. A break inside the game never ends a session. A new module with a session does the same, with a test of a reload, a quick relog and a login after leaving.
- The game never stops for an addon (owner's request of 2026-11-22): work that can take long (a plan over many days, a scan of hundreds of achievements or items) runs as a job of `Skin.lua` (`S.Job(key, work, done)`, the work calls `S.JobTick(share)` in its loops, `S.JobRunning(key)` gives the share for a moving `S.Progress` bar; without the game's clock a job runs at once, so tests see the result at once) and the window keeps the last result meanwhile (Craft Profit has its own `ns.RecalcJob` the same way). Opening a window never calculates: it shows what was calculated or read last, and reads again only what is old. What the bags, the bank, the quest log and the prices say is read once and kept until their event says it changed (Craftsman's Writ's `ns.Cached`/`ns.Invalidate`). Events that come in bursts (`BAG_UPDATE_DELAYED`, `QUEST_LOG_UPDATE`, `GET_ITEM_INFO_RECEIVED`, a page of auctions) redraw once, a moment after the last one, and item requests go out a few at a time. A slow game call (`UpdateAddOnMemoryUsage`) runs at most once in ten seconds. A new long loop calls `S.JobTick` once per pass, with a test that steps the job over several frames.
- Set a font only through `S.SetFont(region, size, flags)` (or `S.Text`/`S.Edit`, which use it): it uses a font family with the game's Cyrillic and CJK fonts, so Russian and Chinese names and chat show on an English client. Never `SetFont(STANDARD_TEXT_FONT, ...)` directly.
- Build the UI in code from the widgets in the module's `Skin.lua`, not from Blizzard's templates, so every part keeps the flat ElvUI-like look. A new kind of widget goes into `Skin.lua`. Do not add XML files.
- The look is rounded, softly: boxes get their corners from `S.Box(f, bg, border, radius, corners)` (the radii `S.R_SM` 3 check boxes, `S.R_MD` 4 buttons, inputs, tabs and list rows, `S.R_LG` 4 cards, tiles and HUD panels, `S.R_XL` 6 windows; only radii that have a ring in `RADII`; a pill takes half its height), switches are pills with a round knob, and every game icon in a window is round in a thin dark gold ring (`S.IconBox`, `S.RING`; a list row's icon is an `S.IconBox` too, never a bare texture). A plain `S.Box(f, bg, border)` stays square, for hairline rows and bars made of parts. A stripe or mark inside a rounded box keeps clear of its corners (inset by the radius). Masks go through `S.RoundMask`, discs through `S.Circle`.
- The look is Gulli Hearth (the classic WoW palette): a window is dense dark brown (`S.BG` 98%, the old name `S.GLASS` points to it; `S.Glass` lays the faint paper grain `Media/Grain` over a window, card, tile or HUD panel, `S.Sweep` draws nothing; behind the hub's centre, low on the right and cut at the window's corner, is the toolkit's satchel as a pale emblem, `Gulli-Toolkit/Art/Mark`, in a warm light; both are drawn by `tools/skin/hearth_art.py`, which also draws `Art/Arc`, the mark of the Ready ring. The emblem comes from `docs/toolkit/emblem.png`, the satchel cut out with a clear background: a picture with its own background shows in the game as a pale square, and the toolkit test checks the corners of `Mark.tga`), the module list and headers darker (`S.SIDE`), cards, tiles and chips a see-through light veil with a thin edge, so the grain and the emblem show through (`S.SURFACE`, `S.RAISED`, `S.CARD_EDGE`; a box of these gets `S.Depth(f, radius)`, the hub's centre has a warm light and the emblem behind it), a window header its own leather band (`S.HeadArt`: grain, a bronze light from the left, a sheen), inputs darkest (`S.INPUT`); edges and dividers are `S.EDGE`/`S.LINE`. Under a window's header runs the one gold line (`S.HEAD_LINE`); there is no other gold line. Each colour has one role and roles never mix: `S.GOLD` is a name or a title, never a button, but for a way back to the page before (`S.Return(button)`: gold with dark text, such as Dungeon Journal's **« All dungeons** and **« Back to the list**; owner's decision of 2026-11-21); `S.GOLD_DIM` a section label in bold capitals (`S.Upper`); the accent, a muted bronze in tone with the brown, never a bright colour (`S.Accent()` parchment for text, `S.FILL` for the main button, a switch that is on and the chosen row at 0.34) is what can be clicked or is chosen; `S.Danger` red only removes something, so a main button is never red; `S.GOOD`/`S.WARN`/`S.BAD` only show a state, and a state never shows by colour or alpha alone (add a dot, a ring or a word). White inside a muted line marks the key number: `S.Emph(text)` (it skips colour codes, links and textures). Text: `S.SetFont(region, size, flags, face)` with face `"body"` (Fira Sans Medium, the default), `"bold"` (Fira Sans Bold) or `"title"` (the game's Friz Quadrata by its path, never `STANDARD_TEXT_FONT`, which other addons replace); sizes are whole numbers and never under 12 (`S.MIN_TEXT`; `S.SetFont` raises a smaller one), titles 16, 20 or 28. The fonts live in `Media/Fonts` (OFL 1.1, cut by `tools/skin/fonts.sh`). Every text that can be long fits on all eight languages without being cut (check German and Russian); an item name may end in "..." only with a tooltip. A frame that must hide what is behind it (a menu over a list) uses `S.SOLID`. Motion goes only through `S.MotionIn`, `S.MotionOut`, `S.MotionSlide`, `S.MotionPop`, `S.Sweep` and `S.Tween` with the durations `S.FAST`/`S.BASE`/`S.SLOW`; each of them does nothing when `S.Calm()` is true (Reduce motion, `GulliToolkitDB.calm`, or the player is in combat), so a calm step must leave the frame in its end state. Motion never scales a frame (a box of many textures scaled by a fraction shows seams): frames fade and slide, and a pressed button darkens. Never animate a secure frame. Optional fields on frames that the fake clients do not know (`gulliMotion`, `gulliTweens`, `glass`) go through `rawget`/`rawset`. Page tabs of a window are `S.PageTabs` (a line under them, which runs on to the right edge); a choice of values stays `S.Tabs` (a segmented track). A control on the row of the page tabs (a search box, a filter) is 28 high and lifted by 3, so it never sits on that line.
- Every window follows the same layout (Gulli UI 2): `S.Window` (header with the module icon, the short title and the slash command), then the body as a column of `S.Card`s placed with `S.Stack`, with `S.PAD`/`S.GAP`/`S.INSET` as the only spacings. Settings are rows in an `S.SettingsCard` (label left, switch or control right); a window's actions go into `S.Footer`, the main one right and `S.Primary` (or `S.Danger` when it removes something), with the status line on its left. Lists use `S.List` with hairline rows (`list.heightOf(item)` gives a row its own height), empty states `S.Empty`, a warning over the body `S.Banner` (yellow, with a cross), numbers `S.Stat`/`S.StatRow`.
- An on/off setting is always a switch: `S.SwitchRow` (or a row of `S.SettingsCard` with `get`/`set`), and `S.SwitchLabel` for one outside a card (a list filter). Never a button that cycles Yes/No or two texts of one boolean; a cycling button is only for a choice of three or more values. Check boxes (`S.Check`) only pick entries of a list (items to remove, dungeons to watch). CI fails on a `{ true, false }` value list or a `L.YES`/`L.NO` text in a `UI.lua`.
- Window sizes fit the hub: a module window is `S.NARROW_W` (540, settings and short lists) or `S.WIDE_W` (832, lists with columns, graphs) wide and at most `S.DOCK_H` (624) high. Inside the hub it gets the full `S.DOCK_H` height, so lists should reach the bottom of the body and the footer stays at the bottom. A page whose content can be taller than the window (a settings page: long texts take two lines in some languages) is an `S.ScrollPage`, built into `page.inner` and closed with `page:SetContent(height)`; `tools/preview` reports a text that runs out of the window as `outside`. A window that stands alone is scaled and raised over the other windows each time it shows (the one opened or clicked last is whole on top, `SetToplevel`); `S.Window` keeps that in front of a module's own `SetScript("OnShow")`, so a window never sets its scale, strata or frame level itself. Change a window's height with `S.FitWindow` or `S.SetWindowHeight`, never `SetHeight` on the window, so a docked window keeps the hub's height. Windows grow with the screen (Gulli Hearth): `S.BaseScale()` is 1 on a 768 unit high screen and at most 1.6, `S.UIScale()` multiplies it by the hub's -/+ scale, and `S.Window` applies `S.FitScale` on each show and on `UI_SCALE_CHANGED`/`DISPLAY_SIZE_CHANGED` (`S.TrackScale`); a docked window has scale 1, since the hub (`ns.HubScale`, 90% of the screen height) is scaled already. Scale a frame only through `S.ApplyScale`, which never touches a protected frame in combat. Notices take `S.BaseScale()`. The toolkit test checks that every module has `window`, `ns.Window` and one of the two widths.
- Colours that carry meaning come from `Skin.lua`: a level gets `S.LevelColor(level)` (the quest log colours: grey, green, yellow, orange, red), an item name `S.QualityHex(quality)`, a state `S.GOOD`/`S.WARN`/`S.BAD` (red for what hurts when it waits, green for what is ready or enough). Money on screen goes through `S.MoneyText(copper, short)` (gold, silver and copper each in its coin colour; from 1 gold up the copper is left out everywhere, also in a module's chat `ns.Money`, owner's decision of 2026-11-21); a module's own plain `ns.Money` is only for chat. Money on a coloured fill (a Primary or Danger button) is `S.MoneyIcons(copper, short)` instead: numbers in the button's text colour with the game's coin pictures, since the coin colours melt into the fill. Money as text is `S.MoneyText(copper)` (gold, silver and copper in their coin colours `S.GOLD`/`S.SILVER`/`S.COPPER`). A price never carries a `~` mark, also when it is an estimate (owner's decision of 2026-11-21): a note in the window says so instead. A stat line of several parts (a run: time, XP, money, kills) colours each part (`S.TIME`, `S.XP`, `S.MoneyText`, `S.KILLS`) and joins them with `S.DOT`. Never a module's own colour table for these.
- Game icons: one icon per settings row, stat tile or list row, from the game's `Interface\Icons`, at the left (`icon =` on the row, `S.IconBox`). One icon keeps one meaning in every module: `INV_Misc_PocketWatch_01` is time, `Spell_Nature_TimeStop` a limit or repeat, `INV_Misc_Coin_02` selling, `Trade_BlackSmithing` repairs, `Interface\Minimap\Tracking\Auctioneer` the auction house and `Interface\Minimap\Tracking\Banker` the bank (the game's own map pictures for them, not an Icons path). Spells and items show their own icon from the game by id (`GetSpellTexture`, `GetItemIcon`), never a fixed path. A module's switches that the hub also shows keep their icons in `ns.OPT_ICON` (key -> path), passed as `icon` in `Register` options. Tabs, filters and pick-one choices (a kind, a role, a roll, a profession) get an icon too: tabs through the `icons` list of `S.Tabs` (the shared meanings are in `S.TAB`: settings, rules, recent, list, group, ...; an icon-only part has an empty label and a `tip`), a button through `S.SetButtonIcon`, a choice that shows what it acts on through `S.IconTile` (the item's own icon by id, a count in the corner, greyed out when there is nothing), roles through `S.ROLE_ICON`, and an icon inside a line of text through `S.IconTag`. Main actions (the footer's Primary or Danger button, OK, Send, Buy) and titles stay text only. A new shared meaning goes into `S.TAB` in `Gulli-Toolkit/Skin.lua`.
- Everything on the game screen outside a window follows Gulli HUD (the `HUD` part of `Skin.lua`): game icons through `S.HudIcon` (state ring: `need` red and pulsing, `soon` yellow, `ok` green; key, count and time on the icon), a caption beside one through `S.HudCaption`, counters through `S.Chip`, small lists through `S.HudList`, and panels through `S.HudPanel`. A notice (a find, full bags, a request, something ready) is `S.Toast{ key, icon, title, text, kind, buttons, seconds }`, which stacks with the notices of every module; only a card with a secure button keeps its own `S.ToastFrame` (MobFinder, with the button on UIParent so the card can show in combat). A frame the player places gets `S.Mover` (built with the frame, never a drag of its own on the frame), a `move(on)` and a `frames` entry in its `Register`. Its show switch, its place and its reset live only there: a module's window and its hub `options` have no show switch, no move or unlock button and no position reset for it (owner's decision). There is no Lock switch in any module (owner's decision): the hub's Unlock mode (**Unlock frames** in the hub's header, `/gulli unlock`, `GulliToolkit.Unlock()` for a module's own button or slash command) shows every frame with its mover over a grid, the panel on the left lists them with their show switches, a click selects one (the arrow keys move it), and the mode ends with **Save and lock** or **Cancel** (every place and switch as before, `S.MoversRestore`); a fight ends it with Save, and it never starts in a fight (`ns.SetMoving` refuses). The hub window steps aside while the mode runs and comes back after Save or Cancel (`ns.hubAside`). A module's `move(on)` that would show, hide or set attributes on a secure frame returns early in combat lockdown, with a test. In the mode the panel lists each frame with its module's icon, and a frame switched off stays placeable but darkened and marked hidden (`m:SetOff`). Every frame on the screen starts hidden: a new frame's show setting defaults to off, and a module whose frame showed before hides it once in older saves behind a `hudHidden` flag that a reset keeps. Notices (`S.Toast`) have one place for all modules, `GulliToolkitDB.toastAt`, set in the same mode. Never draw arrows or symbols the game font lacks (`→`, `≈`, `■`): use `»`, `~` or textures.
- A module opens the world map only through its `ns.OpenMap(id)` (CraftProfit, DungeonPrep, Worth It): out of combat, through `C_Map.OpenWorldMap`, which lets the game open it from its own `WORLD_MAP_OPEN` event, and the global `OpenWorldMap` only on a client without it. An addon's own call of `OpenWorldMap` or `WorldMapFrame:SetMapID` taints the map's pins, and the game then blocks their `SetPassThroughButtons` (`ADDON_ACTION_BLOCKED`). Setting a waypoint (`C_Map.SetUserWaypoint`, `C_SuperTrack`) is fine from anywhere. The fake clients give `C_Map.OpenWorldMap`, and the tests check that the global is not called while it exists.
- Lines in a game tooltip (item, NPC, spell) go only through the Gulli block of `Skin.lua`: a module gives `S.TipProvider(kind, "<Module>", fn)` and returns lines `{ group, left, right, color, rcolor, icon, sub, tag, unless, wrap }`; it never calls `AddLine` or `TooltipDataProcessor` itself (the tooltip of a module's own button or row is not meant). One shared hook (`GulliHUD.tip`, the newest skin copy draws) asks every provider and draws once: a gold line over the block, a faint line over each further group, the group's first line with a small game icon (`S.TipIcon`), lines under it with `sub`. The groups and their order are `S.TIP_GROUPS` (state, quest, stock, price, craft, source, note, id), the modules' order inside a group `S.TIP_ORDER`; a new kind of line joins a group or gets a key there, a new module its place in `S.TIP_ORDER`. Colours by role: `S.GOLD` a quest or boss name, `S.MUTED` a label, `S.TEXT` the key number on the right, `S.GOOD` good news and `S.WARN` an item that will go (always with an icon or a word, never colour alone), class colours for characters, `S.MoneyText` for money, `S.FAINT` for units and ids. A module's phrase starts its line through `S.Cap`, with no module name in front. A line that would repeat another module's line carries `unless = "<tag>"` (Quest Cleaner's "needed for" steps back for the quest's own line, tag `quest`). A provider checks the name, guid and unit it gets for secret values, and its lines function (`ns.TipLines`, `ns.UnitTip`, `J.TipLines`) has a test.
- A window that opens at a place (the mailbox, the auction house, a vendor, the bank, a trainer) closes with it, also when the player walks away: the module runs its closing work through `S.ClosesWith(place, fn)` of `Skin.lua` (`S.PLACES`: the place's open and close events, its `Enum.PlayerInteractionType` and the game's frames), never from its own `_CLOSED` event alone, since the client may send only `PLAYER_INTERACTION_MANAGER_FRAME_HIDE` or just hide its frame then. `fn` runs once per visit, also while the module is paused (Mail, Restock, Crates, Vendor Flip, CraftProfit). A new place gets a row in `S.PLACES`; a new window that opens at a place closes this way, with a test that fires `PLAYER_INTERACTION_MANAGER_FRAME_HIDE` of its kind.
- The place beside the auction house is shared (the side tabs of `Skin.lua`, owner's decision of 2026-11-19): a module with work there gives its window with `S.SideAdd{ key, order, title, icon, window, badge, picked, closed }`, asks for it with `S.SideOpen(key)` at `AUCTION_HOUSE_SHOW` or `MERCHANT_SHOW` (only when it has something to do; the layout anchors to the auction frame when it shows, else to `MerchantFrame`) and takes it away with `S.SideClose(key)`; it never anchors a window to the auction frame itself. One module there: its window stands as it is. Two or more: one window shows and a strip of tabs like a browser's lies over its header (icon, short name, a gold number from `badge`: what is left to do), the tab chosen last comes up first (`GulliToolkitDB.sideTab`), the strip's cross closes them all, and a window that sits in the hub has no tab. Such a window is `S.NARROW_W` by `S.DOCK_H`, like Crates'. The layout gives every window there the same scale and shows it without the opening motion (`quietShow`), so the tabs stand still when the window under them changes. The state is shared by every copy of the skin (`GulliHUD.side`, the newest copy lays it out, `SIDE_V`); a change to these rules gets a case in the Crates test.
- Check a window change without the game in `tools/preview`: `sh tools/preview/icons.sh` fetches the icons once, `lua5.1 tools/preview/shoot.lua <test folder> out.html [scene]` builds the window on fake frames from the module's `tests/<name>/wow.lua` and reports overlapping texts (with `CUT=1` also every text the game would cut with "..."; `LOCALE=deDE` and the like pick the language, `plPL` shows Polish), and `node tools/preview/shoot.js out.html` makes a PNG. `lua5.1 tools/preview/dock.lua <test folder> out.html [scene]` builds the same window inside the hub; check both after a window change. Sample data for each window lives in `tools/preview/scenes.lua`.
- The window must work by mouse and by touch on a phone or handheld: buttons at least 28 pixels high, check boxes at least 26, no text that runs out of its row.
- The addons do not name or promote Runeloader anywhere inside them (texts, TOCs, comments), until the owner says otherwise (owner's decision). A missing module or a newer version only says to install or update it. CI fails on the word in a `Gulli-*` folder.
- Keep comments short and about intent that the code does not show.
- Do not commit release zips or `release.json`; the Release workflow makes them.

### QuestCleaner rules

- Nothing leaves the bags or the quest log without the preview. Every abandon and every delete runs from the **OK** click, for the entries the player left ticked. Never delete from a timer, an event or a slash command.
- Never offer an item a quest that stays in the log may need. When in doubt, keep it: a false "needed" only leaves an item in the bags, a false "not needed" loses it.
- A quest item that stays useful after its quest goes into `PERMANENT` in `Core.lua`, with its name in a comment, when `Data.keep` does not already have it.
- Refresh `Data.lua` with `tools/questcleaner/build_data.py` when QuestieDB releases quest fixes, and bump the version. A new field the cleaner needs goes into the generator, `ns.Data` in `AGENTS.md` and a test with small fake data (`fakeData` in `tests/questcleaner/test.lua`). Keep the generator to the standard library, and never run QuestieDB's own Lua.
- A new rule for what gets offered goes into `Core.lua` (`PlanQuests`, `PlanItems` or `ItemGoes`) with a test in `tests/questcleaner/test.lua`. `UI.lua` only shows the plan.

## Releases

`.github/workflows/release.yml` releases one folder at a time, each on its own tag, so Runeloader sees one package (`Modules.java` in the app, `module_groups` in the index):

| Folder | Tag | Zip |
|---|---|---|
| `Gulli-Toolkit` | `Core-v<version>` | `Gulli-Toolkit-<version>-forever.zip` |
| `Gulli-<Name>` | `<Name>-v<version>` | `Gulli-<Name>-<version>-forever.zip` |

1. In a pull request, bump `## Version` in the TOC of each folder you changed (`x.y.z`), and merge it.
2. Start the Release workflow on `main` from the Actions tab ("Run workflow") with `module` set to `Core` or the module name (`QuestCleaner`), once per changed folder. Or push the tag.
3. The workflow runs every test, zips that folder, writes `release.json` with the `forever` flavor, and publishes the release with both files. It refuses a tag that is already released.

After each release, the `bundle` job (`.github/workflows/bundle.yml`, `tools/bundle/build_bundle.py`) rebuilds `Gulli-Toolkit-All.zip` from the newest published release of every tag group and puts it on the fixed pre-release `bundle`. It stays a pre-release with a `release.json` that names no Forever build, so the index and the app never take it for the core. A new module needs nothing there: every `<Name>-v` group is picked up, so its first release puts it in the zip. The job warns about a `Gulli-*` folder that has no release yet; after adding a module, run its Release and check that the bundle's notes list it. Run **All-in-one zip** from the Actions tab to rebuild it by hand.

Two scheduled jobs keep this honest. **Release health** (`release-health.yml`, every night after the index run) runs `tools/health/releases.py`: a version bumped on main and not released after a day, a release missing from the all-in-one zip, one the index does not show after 30 hours, or a CurseForge upload that failed in the last two days (re-run its failed jobs) opens (or updates) the one issue labelled `release-health`, which closes itself when all is well again. **Game data** (`data.yml`, Mondays) runs every `Data.lua` generator on the newest QuestieDB and Skillet-Classic and the Attune check; when a file changed it opens a pull request (and runs CI on it, since a pull request opened by Actions starts none), else it stays quiet. Such a pull request still needs the version bumps of the changed modules before it is merged. A new generator goes into `data.yml` too. The same job runs `tools/health/forever_content.py`: a dungeon in DungeonPrep's generator that Bulletin does not list (or that has no DungeonPrep icon or entrance), a Forever instance area of QuestieDB's `zones.lua` that DungeonPrep does not list, or a new Forever area not in `tools/health/forever_seen.txt`, or a Forever bag without a source that is not in `tools/worthit/seen.txt`, or a quest bag the BagQuests addon offers that Worth It lacks (`tools/worthit/bagquests.py`), or a Worth It reward without its steps or a Wowhead comments snapshot older than `COMMENT_DAYS` (`tools/worthit/comments.py`; collect it again on a computer), or a Forever pattern whose recipe CraftProfit's `Data.lua` or the Wowhead snapshot does not know and that is not in `tools/health/recipes_seen.txt`, or a Wowhead snapshot older than `WOWHEAD_DAYS` (collect it again on a computer) opens (or updates) the one issue labelled `forever-content`, which closes itself when all is well. A new module with its own dungeon or zone list gets a check there.

**CurseForge** (`curseforge.yml`, run by Release after each release, `tools/curseforge/upload.py`): the projects are in `tools/curseforge/projects.json` (ids, the Forever game version; the token is the `CF_API_TOKEN` secret). A module listed under `separate` (CraftProfit, Crates, DungeonPrep, GroupBuffs; owner's decision of 2026-11-17; Worth It and Vendor Flip since 2026-11-19, My BiS List and Craftsman's Writ since 2026-11-21; they stay out of the toolkit zip) has its own project and uploads its own zip, with an optional dependency on the toolkit (and on the CurseForge slugs in its `optional` list, such as `auctionator`); every other folder ships in the Gulli Toolkit project as one zip of the newest releases, uploaded ten minutes after a release of the core or a small module (a newer release cancels that wait) and only with what was released since the last `upload toolkit` job, so a batch of releases makes one toolkit file and CurseForge never gets the same zip twice (it rejects a duplicate). Not a cron: GitHub ran this repository's schedules hours late. One folder is never in two projects. A new module goes into the toolkit zip by itself; giving it its own project is an owner's decision, and moving a folder out of the toolkit later removes it for players who installed the toolkit, so it gets its own project only before its first upload. Without the secret or an id the job does nothing. Each project has its own upload queue (`upload.py --route`): a batch of releases never drops a module's upload,. "Run workflow" with `toolkit` uploads the toolkit now (when something changed), with a tag that project, with `all` every project once.

Never tag the core with a plain `v<version>`: the core is `Core-v…`. A tag prefix such as `release-` or `beta-` is not a module (`NOT_MODULES` in the index and the app).

The owner asks for a release after every merged bug fix and after each batch of features: bump the version and run the workflow once the pull request is merged with green CI. Runeloader shows the new version after the next nightly index run. Installing the core in Runeloader installs every module.

The tag names, asset names and `release.json` are what Runeloader and its index read. A change to them is a change in runeloader-index too.

## Language

- Write code, identifiers, comments, commit messages, issues, pull requests and these instructions in English.
- `README.md` (the toolkit) and `docs/<name>/README.md` (each module) are pages for players. It is in plain English (about B1 level): short sentences, no jargon in the main part. It keeps this order: the wordmark, a one-line pitch, features, install steps, FAQ. Technical details go inside `<details>` spoilers. Their images live next to them in `docs/<name>/` and stay small (under about 400 KB each; use JPEG for large photo-like images).
- Every addon speaks the same languages as the Runeloader app: English (the base and the fallback), Deutsch, Español, Français, Polski, Português, Русский and 中文.
  - Put no UI text in `Core.lua` or `UI.lua`. Add every new key to every language table in the addon's `Locales.lua` in the same pull request; its test fails on a missing key or a different number of placeholders.
  - Every addon always follows the game client's language (`GetLocale`), like the app follows the system language. There is no language picker (owner's decision).
  - A new language needs a table in `T`, an entry in `TAGS`, its client locales in `CLIENT` when the game has them, and a `## Notes-<locale>` line in the TOC.
  - Save a text by its key (as `item.why` does), not as a translated string.
  - A text a player reads that comes from game data or a guide (objectives, guide notes, players' comments) is in every language too, never English alone (owner's decision of 2026-11-21). The generator takes the game's own translation where the data has one (QuestieDB's `l10n`), and the rest through `tools/i18n/i18n.py`: `sync(domain, texts)` keeps the cache `tools/i18n/<domain>.json` (English -> language -> text, `_need` for a text the game has in some languages), so a data update translates only its new texts (`i18n.py pending`, `export`, `merge`; names stay in English). The module reads them from one `Data_<lang>.lua` per language, which starts with `if ns.lang ~= "<lang>" then return end`, and falls back to English. `tools/health/forever_content.py` reports a text still to translate. A new module with such texts gets its domain there, its `Data_<lang>.lua` files in the TOC and a test that reads one.

## Verification

CI runs these on every pull request to `main`. Run them before you open one:

```sh
for f in Gulli-*/*.lua Gulli-*/Tweaks/*.lua tests/*/*.lua; do luac5.1 -p "$f"; done
for t in tests/*/test.lua; do lua5.1 "$t"; done
```

CI also runs `python3 tools/lint/luacheck.py` (luacheck, only the warnings that are bugs: a global that is not ours set or changed, a local read but never set such as `local a, b = f and f()`, unreachable code) and `python3 tools/apicheck/check.py <Blizzard_APIDocumentationGenerated>` (an event registered with a plain `RegisterEvent` or compared as `event == "X"` that the client does not have, a `C_` function the client documentation lacks called without a check, a classic-only global in `CLASSIC_ONLY` called without a check). A finding that was looked at and is fine goes into `tools/apicheck/allow.txt` with a comment; a new classic-only global goes into `CLASSIC_ONLY`. Clone the documentation of the Forever client with `git clone --depth 1 --branch forever --filter=blob:none --sparse https://github.com/Gethe/wow-ui-source` and `git sparse-checkout set Interface/AddOns/Blizzard_APIDocumentationGenerated`.

A module that removes, sells or takes things has a test with random states (`random ...` in its test: QuestCleaner, BagSpace, Merchant, Mail) that checks what must never go, never goes; a new module that removes things gets one, with a fixed seed and a check that the rounds did offer things.

CI also checks that every folder has a Forever TOC that lists all its Lua files, and that every module TOC has `X-Gulli-Module` and `OptionalDeps: Gulli-Toolkit` and a `tests/<name>` folder.

The fake clients cannot show a window or run the real game rules. For a change to a module's `Core.lua` or `UI.lua`, also try it in WoW Forever: copy the folder (and `Gulli-Toolkit`) into `Interface/AddOns`, `/reload`, open it from `/gulli` and from its own slash command. For QuestCleaner and BagSpace, check the preview before **OK**, with a character whose quests and items you can lose. For Restock, check the list at a vendor before **Buy**. Attach a screenshot of a changed window to the pull request. Say what you checked, on which client and device, and report any check you could not run.
