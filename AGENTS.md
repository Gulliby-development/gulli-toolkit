# Working on Gulli Toolkit

These instructions apply to every coding agent (Claude Code, GitHub Copilot, Codex and others) and to human contributors.

## Project

Gulli Toolkit is a set of our own small World of Warcraft addons for WoW Forever, in one repository. Each top-level `Gulli-<Name>` folder is one addon as it goes into `Interface/AddOns`: `Gulli-Toolkit` is the core (the hub), every other folder is a module (`Gulli-QuestCleaner`, `Gulli-Bulletin`, `Gulli-BagSpace`, ...).

- WoW Forever is Vanilla content on the Retail engine. The API is Retail's (`C_QuestLog`, `C_Container`, `C_Item`, `C_AddOns`); the quest and item data are Vanilla's. Keep a fallback to the old global API where it costs one line, so an addon also loads on a client without the `C_` namespaces.
- TOC: `## Interface: 16001`. The index and Runeloader treat `## Interface: 160xx` as a Forever build.
- Our own addons are all named `Gulli-<Name>` (G-U-L-L-I, after the nick Gulliby). The folder, the TOC and the title use that name; the module key is `<Name>`.
- Plain Lua 5.1 with no libraries (no Ace3, no LibStub). The whole UI is built in code.
- It ships through [Runeloader](https://github.com/Gulliby-development/runeloader): the [runeloader-index](https://github.com/Gulliby-development/runeloader-index) lists it from `seeds.txt` as one package, the core plus one entry per module.
- The repository is GPLv3 (QuestCleaner carries QuestieDB data).

## Modules and the core

- A module is a normal addon that works alone. It never needs the core. Its TOC has `## Interface: 16001`, `## Version: x.y.z`, `## OptionalDeps: Gulli-Toolkit` (so the core loads first), `## X-Gulli-Module: <Name>` (so the hub lists it even when it is switched off), `## IconTexture`, `## Category: Gulli` and `## X-License: GPL-3.0`. CI checks these lines.
- At file load a module registers with the hub: `if GulliToolkit and GulliToolkit.Register then GulliToolkit.Register({ key = "<Name>", open = function() ... end, icon = ..., slash = "/g.." }) end`. `title` and `desc` are optional; the hub falls back to its own `M_<Name>`/`D_<Name>` texts, then to the TOC `Title` and `Notes`. `category` (a key of `ns.CATEGORIES`) is optional too: a known module has its group in `ns.CATEGORY_OF`, another one may name it in Register or in its TOC (`## X-Gulli-Category`), else it is `Other`. `options` is an optional list of the module's main switches (`{ label, get, set, icon, tip }`, `icon` and `tip` optional, at most six), with the same saved keys as its window; the hub's search finds a module by them. `summary` is an optional function that returns one short line (and optionally an icon path) for the hub's home page, such as "Level 24 in 1 h 10 min" or "2 entries left"; it must be cheap and safe to call at any time, and return nil when there is nothing to say. `move(on)` unlocks (true) or locks the module's frames on the screen for `/gulli move`; `reset()` puts the module's settings back to their defaults for the hub's **Reset to defaults** (it must refresh the module's window and frames). `window` gives the hub the module's main window so it can show it inside `/gulli`: `window = function() return ns.Window and ns.Window() end`, where `UI.lua` has `ns.Window()` (builds the `S.Window` once and returns it) and `ns.Toggle()` calls `S.ToggleWindow(ns.Window())`, so the slash command takes a window out of the hub instead of closing it. Work that `ns.Toggle` does when the window opens also runs from an `OnShow` hook when `self.docked`, because the hub shows the window itself. A module with several windows gives its settings window (Mail's mailbox panel stays at the mailbox). `Register` accepts `.` and `:` calls. A new field in this table is optional for the core; the core keeps `GulliToolkit.api` and raises it on a breaking change.
- The core offers two services a module may use, always behind a check that the core is loaded (`if GulliToolkit and GulliToolkit.IsProtected then ... end`):
  - `GulliToolkit.IsProtected(itemID)`: items the player protected in the hub. A module that sells, deletes, moves or offers bag items skips them (QuestCleaner, BagSpace). A new module that removes items checks it too, with a test.
  - `GulliToolkit.Notify(key, text)`: one line in the hub's **Recent** feed (newest first, `FEED_MAX` lines). Use it for news the player may miss in chat (a limit reached, a cooldown ready), not for every event.
- Each module has its own copy of `Skin.lua` (same look, no shared code at run time). The copy in `Gulli-Toolkit/` is the original: change only that one, then run `tools/skin/sync.sh` to copy it into every module. CI fails when a copy differs.
- A new module gets: its folder `Gulli-<Name>/`, its tests in `tests/<name>/` (lowercase, its own fake client `wow.lua`), its player page `docs/<name>/README.md` with its images, a row in the module table of `README.md`, its key in `ns.KNOWN` in `Gulli-Toolkit/Core.lua` with `M_<Name>` and `D_<Name>` in every language of `Gulli-Toolkit/Locales.lua`, and its tag group in [Releases](#releases).

### Gulli-Toolkit (the core)

- `Gulli-Toolkit.toc` loads `Locales.lua`, `Core.lua`, `Skin.lua`, `UI.lua`. It keeps `GulliToolkitDB` account-wide (`protected`: item id -> true, `feed`: the Recent lines, `scale`: the hub's size, `minimap`: `hide` and `angle` of the minimap button, `last`: the module the hub opens on, `seen`: module key -> version last opened).
- `Core.lua` holds the global `GulliToolkit` (`modules`, `Register`, `Open`, `api`), the list of known modules (`ns.KNOWN`), the hub rows (`ns.List`: known modules first, then any other installed `X-Gulli-Module`, each `ready`, `off`, `reload`, `blocked` (enabled, but the game refuses to load it; `reason` is the game's `IsAddOnLoadable` reason, shown through `ns.ReasonText`) or `missing`), switching a module on or off in the game's AddOns list (`ns.SetEnabled`: for this character by name and for every character, then `SaveAddOns`; it takes effect after a reload and reports when the game did not take it; there is one state, the game's: `row.on` is always read from the game (enable state and `IsAddOnLoadable`), never kept by the hub, and a row whose switch and what runs disagree is `reload`, see `ns.NeedsReload`), the protected items (`Protect`, `IsProtected`, `ns.Protected`), the feed (`Notify`, `ns.Feed`) and `/gulli` (`/gulli <module>` opens a module, `/gulli protect <item link>` protects or frees an item).
- `UI.lua` is the hub window (owner's decision): on the left a narrow list of the modules (icon, name, small on/off switch; the name's colour shows `reload`, `blocked` or not installed, a dot on the icon marks `row.new`), grouped by `ns.Groups` with `on/total` and one switch per group (`ns.SetGroup`), the search on top (it also finds a module by its `options` labels and `tip`s; Enter opens the first), **Protected items** and **Reload** at the bottom. In the centre always one page: a click on a module docks its window there at once (`enter`, `ns.Enter` for the tests; `f:Dock` with **<** back to home, the on/off switch in its header). A narrow window keeps the module card beside it (icon, group, state, description, command, version, memory, **Reset to defaults** when the module gives `reset`, **Open in its own window**); a wide one takes the whole centre. A module that is off, waits for a reload, is refused or is not installed shows a page that says so; a module without `window`, or with a window bigger than the centre, opens alone as before. With nothing chosen the centre is the home page: the modules' `summary` lines as tiles (`ns.Summaries`, a click opens the module), the **Recent** feed with `ns.Ago` times (a click opens the module, **Clear**), and **Quick setup** (the presets of `ns.PRESETS` through `ns.ApplyPreset`, **Move frames** = `ns.SetMoving`, **Export / import**, the **Minimap button** switch). Protected items and Export / import are pages in the centre too. The hub opens on the module that was open last (`GulliToolkitDB.last`, cleared by **<** and Home). The window is `S.NARROW_W` + the card wide and `S.DOCK_H` + the header high (1086 by 700), and `ns.HubScale` shrinks it to fit the screen times the player's **-**/**+** scale (`GulliToolkitDB.scale`). It also adds the page under Options, AddOns, and the one minimap button (`ns.BuildMinimap`: a click opens the hub, a drag moves it around the minimap; `ns.MinimapOffset` places it on a round or square minimap; the **Minimap button** switch on the home page and on the Options page, and `/gulli minimap`, hide it). Modules get no minimap buttons of their own: the hub's button and the addon compartment open them. It only shows what `Core.lua` holds.
- More in `Core.lua`: `GulliToolkitDB.seen` (module key -> the version the player last opened; a module whose TOC version differs is `new`, the first version seen is only noted), `ns.Export`/`ns.Import` (every saved variable named in the TOCs, `GULLI1:` and a plain serializer, `ns.Deserialize` reads only what `ns.Serialize` writes and never runs the text; import sets only `Gulli...DB` globals and asks for a reload), the version check in the group (prefix `GulliTK`, `V|Core=1.6.0|XP=1.4.0`, at most 240 characters a message, at most once a minute; a newer version is told once per session; add a new message type, never change this one), `ns.Memory` and `/gulli help` (`ns.HelpLines`: the toolkit's commands, then every ready module's `slash`).
- A new preset goes into `ns.PRESETS` (known module keys only) with a `PRESET_<Key>` text in every language; the test checks both.
- A new module group gets a key in `ns.CATEGORIES`, a `CAT_<Key>` text in every language and a case in `tests/toolkit/test.lua`.
- The game's addon calls go through the wrappers at the top of `Core.lua`, with a fake in `tests/toolkit/wow.lua`.

### Gulli-QuestCleaner

- `Gulli-QuestCleaner.toc` loads `Locales.lua`, `Data.lua`, `Core.lua`, `Skin.lua`, `UI.lua` in this order. It keeps `GulliQuestCleanerDB` account-wide (`quests`, `items`, `keep`, `keepClass`, `keepDungeon`, `keepElite`; `level` only as the start value for older saves) and `GulliQuestCleanerCharDB` per character (`level`, `last`). The tests load the files in the TOC order.
- `Data.lua` is generated by `tools/questcleaner/build_data.py` from the QuestieDB Forever data; never edit it by hand. `ns.Data` has `need` (quest item -> quests that ask for it), `quest` (quest -> level, race mask, class mask, max level, quests that close it), `keep` (quest-class rewards no quest asks for), `itemStart`, `chain` and `class` (quest id sets). Race masks pass 2^32 on Forever: test bits with arithmetic, not `bit.band`. Because of this data the addon is GPLv3.
- `Locales.lua` has the texts of every language: `ns.L` reads the game client's language and falls back to English.
- `Core.lua` holds the rules and touches the game: the quest log scan (`ns.Quests`), the plan (`ns.PlanQuests`, `ns.PlanItems`, `ns.ItemGoes`), the run (`ns.Run`, `ns.Leftover`), the slash commands and the saved variables.
  - A quest is planned when its level is at or below the entered level (or the gray level, `ns.GrayLevel`). Headers, hidden quests and quests without a level stay, and so do class, dungeon/raid and elite quests while their switch is on (`protectedBy`). A quest that an item started is planned unticked (`warn = "TAG_ITEM"`); a chain quest is marked (`TAG_CHAIN`).
  - Each quest keeps its zone: the quest log header above it. `ns.PlanQuests` sorts by zone in quest log order, then by level; `ns.Zones` groups the plan by zone for the window.
  - A bag item is a quest item when its class is Quest (12), the game marks it as a quest item, or it starts a quest.
  - A quest item is offered when no quest that stays in the log needs it. "Needs" means its name is in the quest's objectives, summary or description, or it is the quest's usable item. The planned quests that need it become its `links`; an item with no link is listed under "No quest".
  - The data adds to this: a quest in the log that the data lists for the item keeps it or links it like the text does. An item the data lists for a quest above the entered level that the character can still take (`canTake`) is not offered; `ns.PlanItems` returns those items as its second value. The data only ever adds reasons to keep an item.
  - An item that starts a quest is offered only when that quest is already done.
  - `PERMANENT` lists quest items that stay useful after their quest (dungeon keys, attunements, raid summoning items), and `Data.keep` adds the quest-class rewards no quest asks for. They are never offered. Items the player unticked go into `keep` and are not offered again until `/gqc reset`.
  - `ns.ItemGoes`: an item goes only when it is ticked and every quest it is linked to goes too.
- `Skin.lua` is the flat look in the spirit of ElvUI: dark panels with 1 pixel borders, the class colour as the accent, flat buttons, check boxes, edit boxes and a thin scroll bar, all drawn from plain textures.
- `UI.lua` is the window: the setup view (level with a **Gray** button, what to clean, the three protection switches) and the preview (zones with their quests on the left, items on the right, a line from each quest to its items; a zone row ticks or unticks all its quests; below, the quest log and bag places before and after **OK**). It shows what `Core.lua` planned and never decides on its own what to remove.
- With a merchant open (`MERCHANT_SHOW`), `ns.Run` sells an item that has a price instead of deleting it. It saves what it removed in `last` for `/gqc last`. When the log is two quests from full, `QUEST_ACCEPTED` prints one chat hint; it never removes anything.
- Removing things runs inside the **OK** click, because the game lets an addon delete a picked-up item only inside a hardware event. The game confirms a delete later, so the cursor can still hold the item right after `DeleteCursorItem`: `ns.Run` never stops on that, it clears the cursor and goes on, so one **OK** tries every ticked item. A second later `ns.Leftover` shows what the game really refused, and the player presses **OK** again only for that.

### Gulli-MobFinder

- `Gulli-MobFinder.toc` loads `Locales.lua`, `Data.lua`, `Core.lua`, `Skin.lua`, `UI.lua` (`/gmf`). `GulliMobFinderDB`: `names`, `mobs` (lower-case name -> `off`, `exact`, `count`, `zone`, `at`, read through `ns.Info`), `ids` (npc id -> name, from the zone rares), `history` (at most `ns.HISTORY_MAX`), and the switches in `DEFAULTS`. `ns.Scan` reads visible nameplates (`NAME_PLATE_UNIT_ADDED` and a poll every N seconds), with `sources` also the target, mouseover and the group's targets, and with `vignettes` the minimap rare markers. It skips secret names (`issecretvalue`), players, player-controlled units and, with `skipTapped`, mobs another player tagged. A mob alerts again only after it was out of sight and `cooldown` passed. `Data.lua` (`ns.RARES`: area id -> rares) is generated by `tools/mobfinder/build_data.py` from QuestieDB; never edit it by hand. Rares match by npc id (`ns.NpcID`) and zones by `C_Map.GetAreaInfo` names, so they work in every client language. It never targets on its own: the card's `GulliMobFinderTarget` is a secure button with a `/targetexact` macro, set only out of combat (a find in combat waits for `PLAYER_REGEN_ENABLED`), and the Target key binds to it with `SetOverrideBindingClick`. Finds are shared on the prefix `GulliMF` (`F1\tname\tmap\tx\ty`); the format is a contract between versions: add a new message type, never change this one. A new setting gets a default in `DEFAULTS`, a row in the window and a test.

### Gulli-GroupBuffs

- `Gulli-GroupBuffs.toc` loads `Locales.lua`, `Buffs.lua`, `Core.lua`, `Skin.lua`, `UI.lua`. It keeps `GulliGroupBuffsCharDB` per character (`who`, `show`, `combat`, `low`, `groupMin`, `thorns`, one key per `B.CHOICES` list, `locked`, `key`, `point`, `pets`, `mana`, `where`, `readyCheck`, `marks`, `focus`, `raidGroups`, `perSize` with `size.<solo|party|raid>` overrides read through `ns.Setting`, `watch` by buff key, `bless` by class or role). A new setting gets a default in `ns.DEFAULTS`.
- It is a clean-room take on HealKit's Quick Buff. HealKit is "All Rights Reserved": never copy its code, texts or icons.
- `Buffs.lua` lists the buffs per class by rank 1 spell id (a pick-one family names its list in `B.CHOICES` and its start value in `B.CHOICE_DEFAULT`) (`who`: `all`, `mana`, `self`, `thorns`, `blessing`; `group`: the party-wide spell). Names come from the game (`ns.SpellName`), so spells need no translation. A new buff or class goes here, with a spell name in `W.SPELLS` and a case in `tests/groupbuffs/test.lua`.
- `Core.lua` holds the rules and reads the game; it never casts. `ns.Plan` returns the missing buffs in casting order (you first, then the group in roster order, then a friendly target) and, as a second value, the ones out of range. A group spell replaces the single casts of one party when `groupMin` of it need the buff and the spell is usable (has its reagent). A unit whose auras the game hides (secret values) is skipped, never nagged. Pets follow their owner (`who = "all"`, and `mana` when they have mana); a unit whose cast just failed is skipped for `ns.SKIP_SECONDS` (`ns.Skip`). `ns.Status` gives why nothing is cast; a new reason gets an `ST_` text in every language and a test. The marks on the game's party and raid frames are textures of our own, kept in a weak table, never fields on those frames.
- `UI.lua` holds the secure buttons: `GulliGroupBuffsButton` (the big one, also on the key through `SetOverrideBindingClick`) and its small buttons. Their attributes change only out of combat. On `PLAYER_REGEN_DISABLED` the plan goes into `gb-spell<i>`/`gb-unit<i>`/`gb-count` of the big button, and `ns.COMBAT_SNIPPET`, wrapped on its `OnClick`, aims it at the next living unit of that list on each press, wrapping at the end. The snippet may use only what the restricted environment has (`PlayerInCombat`, `SecureCmdOptionParse`, the frame handle); the test runs it with only those. In combat the insecure code changes only textures and texts.

### The smaller modules

Each one loads `Locales.lua`, `Core.lua`, `Skin.lua`, `UI.lua` (DungeonPrep adds `Data.lua` after `Locales.lua`). `Core.lua` holds the rules and the game calls, `UI.lua` only shows them. Every module is tested in `tests/<name>/`.

- **Gulli-Bulletin** (`/gbul`, `GulliBulletinDB`: `minutes`, `myLevel`, `other`, `only`, `alert`, `sound`, `chat`, `posts`, `blockNames`, `blockWords`, `watch`, `role`, `feed`). Reads `CHAT_MSG_CHANNEL`, `SAY` and `YELL`. `ns.Classify` sorts a message into `GROUP`, `WTS`, `WTB`, `CRAFT`, `GUILD` or `OTHER`, finds the dungeon (`ns.DUNGEONS`: key, area id or nil for a Forever-only area named by `DG_<KEY>` in Locales, words) and the role (`LFM`, `LFG`). Only dungeons WoW Forever has are listed. A short or common word starts with `~` (weak): it names the dungeon only in a message that already asks for a group, and never as `<word> me`; each one gets a test it must not match. `ns.db.only` (dungeons the Groups tab shows, none = all) and `ns.db.alert` (a new group there plays a sound, writes in chat and calls `Notify`; `sound`, `chat`) are set on the Setup tab. The posts live in `db.posts`, so the board survives a /reload. An LFM keeps the roles it asks for (`ns.Needs`, words in `ROLE_WORDS`), the poster's class (from the chat GUID) and the first item link. **Ask** whispers `ns.AskText` (level, class, `db.role`). Blocked players and words never reach the board (`ns.Blocked`); watched words ring like an alert (`ns.Watch`). **My LFM** calls `GulliQuickChat.OpenLFM(key)` when Quick Chat is loaded: that global is the contract between the two modules. One poster keeps one post per kind (`ns.Add`); posts older than `minutes` go. A new kind gets its words in `WORDS` (in `Core.lua`), a tab and a test; a new dungeon word goes into `ns.DUNGEONS` with a test. Matching is on lowercased text (`lowerUtf8` handles Cyrillic and Latin-1). Messages may be secret values in WoW 12: skip them (`issecretvalue`).
- **Gulli-PartyQuests** (`/gpq`, `/gpq share`; `GulliPartyQuestsDB`: `zoneOnly`, `autoShare`, `track`, `tooltip`, `sound`, `nAccept`, `nObjective`, `nComplete`, `nTurnin`, `nAll`; defaults in `ns.DEFAULTS`, read through `ns.Get`). `ns.Ours` compares the player's log with each member (`C_QuestLog.IsUnitOnQuest`) into cells `has`, `done`, `no`, `turned` (did it before) or `unknown` (offline), with progress when the member's module sent it; `ns.Status` says whether a member runs the module (`fresh`, `stale` after 5 minutes, `none`, `offline`); `ns.Summary` is the line about the group. `ns.Theirs` comes from addon messages on the prefix `GulliPQ` (`ns.Encode`/`ns.Receive`, at most 240 characters per message): inside a `B`...`E` list, `Q` quest ids, `O` objectives, `C` quests of the others the sender did before; alone, `R<id>:<name>` asks one member to share and `T<id>` asks everyone to track. The message format is a contract between versions: add a new message type, never change an old one. `ns.Diff` turns two lists of a member into news (`ns.Announce`, each kind behind its switch); `ns.ShareAll` shares one quest per second; `ns.ShareReply` reads the game's share answers. The tooltip lines (`ns.TooltipLines`) match a mob or item name to the whole objective name.
- **Gulli-InstanceLimit** (`/gil`, `GulliInstanceLimitDB`: `entries` (with run stats `out`, `secs`, `xp`, `money`, `kills`), `open`, `limit`, `dayLimit`, `confirmed`, `fromExit`, `warnAt`, `warnDayAt`, `freeAlert`, `sound`, `summary`, `tellGroup`, `sync`, `badgeMode`, `badgeScale`, `badgeAlpha`, `badgePoint`; defaults in `ns.DEFAULTS`). Counts a party or raid map once until a reset, a group change or an hour (`ns.Entered`, `ns.Reopen`); `ns.Status` gives what is left, the wait and `by` (the limit that blocks); `ns.When` is the entry or, with `fromExit`, the exit. `TRANSFER_ABORT_TOO_MANY_INSTANCES` teaches it the real limit and confirms it (`ns.Refused`); more entries than the limit raise it. `ns.Tick` says once when an entry frees. Group members share over addon messages on `GulliIL` (`RESET\t<dungeon>`, `STATE\t<hour>\t<day>\t<wait>`, `HELLO`): add a new message type, never change an old one. A new counter mode goes into `ns.BADGE_MODES` with a `MODE_<KEY>` text. The Forever limits are not verified; keep them settings.
- **Gulli-Attune** (`/gat`, `GulliAttuneDB.chars`). `ns.RAIDS` lists each raid attunement and quest-chain dungeon key with its quest chain (or `anyOf` steps), faction, the item it gives and where the first step starts, raids first, then the keys. Only what WoW Forever has: a raid that Forever has not opened (Molten Core, Blackwing Lair, Naxxramas today) is not listed, and comes in when Blizzard opens it. A new raid, key or step goes there with a `RAID_<KEY>` text in every language and a test; quest ids come from QuestieDB. `tools/attune/check_data.py <questiedb>` checks every step against the Forever data and lists new candidate quests not in `tools/attune/seen.txt`.
- **Junk rules** (`Junk.lua`, shared by Merchant and BagSpace as `ns.J`). The original is `Gulli-Merchant/Junk.lua`; `tools/junk/sync.sh` copies it into `Gulli-BagSpace`, and CI fails when the copies differ. `J.Tier(it, opts)` says what is junk (1 gray or the "always sell" list, 2 white gear and, with `opts.unusable`, bound gear the class cannot use (`J.CAN_USE`), 3 other white items); `J.Never` keeps quest items, keys, profession tools (`J.TOOLS`), fishing poles, equipment set items, the hearthstone and protected items out. Each addon keeps its own `junk` list in its saved variables and attaches it (`J.Attach`), so `J.SetAlways` marks both. `J.Sell` sells in steps of 12; `J.InstallMarks` adds the tooltip line, the coin on junk slots and Alt+click once, even with both loaded. A new junk rule goes into `Junk.lua` with a test in both modules' tests.
- **Gulli-BagSpace** (`/gbs [n]`, `/gbs reset`, `/gbs sort`; `GulliBagSpaceDB`: `want`, `warnAt`, `keep` (items the player unticked), `junk`, `unusable`, `counter`, `popup`). `ns.Plan(want)` merges stacks first (`ns.Merges`), then offers items by `ns.Tier` (the junk rules, minus `keep`). An item worth `AH_FACTOR` times more at the auction house (Auctionator) is offered unticked. Selling runs in steps of 12 and deleting in the **OK** click, like QuestCleaner; `ns.Leftover` shows what the game kept; merging runs in small timed steps (`ns.StartMerges`). On "Inventory is full" a popup offers **Free 1 slot** (`ns.FreeOne`, in the click).
- **Gulli-DungeonPrep** (`/gdp [KEY]`). `Data.lua` is generated by `tools/dungeonprep/build_data.py` from QuestieDB; never edit it by hand. A quest belongs to a dungeon when its zone is the dungeon, or its mobs and objects spawn only there, or most of its drops come from there, within the dungeon's level window. The generator leaves out repeatable quests (`specialFlags` 1) and item exchanges started and finished by the same object (the Sparklematic 5200), and writes each quest's faction (`A`/`H`, from the race mask, else from its NPCs) and the starter's map position. `ns.Quests` splits them into `log`, `take` and `later` (with `why`) for the player's faction, race and class; `ns.Route` turns `take` into stops (the player's zone nearest first from `ns.Here`, then the same continent, the other one, and inside the dungeon last) and `ns.SetPin` puts a map pin on one. Colours come from `ns.Difficulty` (quests) and `ns.DungeonDifficulty` (dungeon ranges) with the game's steps; each dungeon has a game icon in `ns.ICONS`. A new dungeon gets an icon there and its row in the generator's `DUNGEONS`. `ns.Checklist` checks durability, bag space, food and drink and the hearthstone.
- **Gulli-QuickChat** (`/gqk`, `/gqk wheel`; `GulliQuickChatDB`: the settings in `ns.DEFAULTS` (`channel`, `autoBusy`, `busyMinutes`, `sound`, `remind`, `keepLog`, `always`, `wheelKey`, `panelShow`, `panelLocked`), `phrases`, `chan`/`fav`/`cat` by phrase text, `history` (the last `ns.HISTORY_MAX` sent), `log` (whispers by player, `ns.LOG_MAX`), `panelPoint`). Phrases with tokens (`ns.Fill`: `{target}`, `{zone}`, `{me}`, `{level}`, `{targetclass}`, `{targetlevel}`, `{hp}`, `{mana}`, `{leader}`, `{item}`, `{quest}`); a new token goes into `ns.Fill`, the `TOKENS` text and a test. Default phrases are `P1`..`P<ns.DEFAULT_COUNT>` with their category in `DEFAULT_CAT`. ## Task workflow

- Track planned work as GitHub Issues in this repository, not in Markdown files or TODO comments. Before you start, find the issue for the task or open one. Record a new idea, a follow-up or a deferred item as an issue.
  - Issue types: Task, Bug or Feature.
  - Labels: `idea` (not decided yet), `deferred` (agreed for later), `needs-owner` (only the owner can do or decide it), `verification` (needs the real game), and `area:core|quests|items|ui|locales|build|ci`, and `module:<name>` for the module it is about.
  - Put `Priority: P0|P1|P2` on the first line of the issue body. P0 blocks current work or a release, P1 is next, P2 is later or an idea.
- Before you open or extend a Bug issue, follow the [file-issue skill](.agents/skills/file-issue/SKILL.md). It finds the root cause and sweeps the code for every other place with the same defect. A pull request that fixes such an issue fixes every place the issue lists and reports the result in a `## Sweep` section of its description.
- Every Feature and Task issue has a `## Maintainability` section. It names the rule a later change must follow when the task adds something that later code must extend (a new module, a new item rule, a new language, a new saved setting). It says `None` when nothing needs extending. The pull request that adds such a mechanism adds its rule to this file.
- Start every task on its own branch from an up-to-date `main`:
  - new feature, documentation, CI or refactor: `feature/<name>`;
  - bug fix: `bugfix/<name>`.

  `<name>` is a few lowercase words joined by hyphens. Do not use other prefixes (`docs/`, `fix/`, `claude/`, `copilot/`) or generic names such as `patch` or `update`. If your tool proposes a default branch, rename it before the first push. CI fails a pull request whose branch breaks this rule; only Dependabot's `dependabot/` branches are exempt.
- Commit working states on the task branch. Before each commit, run the tests of every module you touched (`lua5.1 tests/<name>/test.lua`), so every commit passes.
- A pull request that finishes an issue says `Closes #N` in its description. Use `Refs #N` when the pull request does only part of it.
- Before you finish a task, check `README.md` and the module's `docs/<name>/README.md` against your change and update it in the same pull request: features, commands, button names, FAQ answers and images must match the addon as it is after the merge. Say in the pull request description that you checked it, or what you changed.
- When the task is complete and [Verification](#verification) passes, open a pull request to `main`. `main` takes changes only through pull requests with green CI. Do not push to `main` directly.

## Working conventions

- Keep the addon free of libraries. Use the game's API and Lua 5.1 only. A new dependency needs an issue and the owner's decision first.
- The game API goes through the small wrappers in the module's `Core.lua` (QuestCleaner: `slotInfo`, `numSlots`, `questInfo`, `pickup`, ...), which pick the `C_` function and fall back to the old global. A new game call gets such a wrapper and a fake in the module's `tests/<module>/wow.lua`.
- Build the UI in code from the widgets in the module's `Skin.lua`, not from Blizzard's templates, so every part keeps the flat ElvUI-like look. A new kind of widget goes into `Skin.lua`. Do not add XML files.
- Every window follows the same layout (Gulli UI 2): `S.Window` (header with the module icon, the short title and the slash command), then the body as a column of `S.Card`s placed with `S.Stack`, with `S.PAD`/`S.GAP`/`S.INSET` as the only spacings. Settings are rows in an `S.SettingsCard` (label left, switch or control right); a window's actions go into `S.Footer`, the main one right and `S.Primary` (or `S.Danger` when it removes something), with the status line on its left. Lists use `S.List` with hairline rows, empty states `S.Empty`, numbers `S.Stat`/`S.StatRow`.
- Window sizes fit the hub: a module window is `S.NARROW_W` (540, settings and short lists) or `S.WIDE_W` (832, lists with columns, graphs) wide and at most `S.DOCK_H` (624) high. Inside the hub it gets the full `S.DOCK_H` height, so lists should reach the bottom of the body and the footer stays at the bottom. Change a window's height with `S.FitWindow` or `S.SetWindowHeight`, never `SetHeight` on the window, so a docked window keeps the hub's height. The toolkit test checks that every module has `window`, `ns.Window` and one of the two widths.
- Colours that carry meaning come from `Skin.lua`: a level gets `S.LevelColor(level)` (the quest log colours: grey, green, yellow, orange, red), an item name `S.QualityHex(quality)`, a state `S.GOOD`/`S.WARN`/`S.BAD` (red for what hurts when it waits, green for what is ready or enough). Never a module's own colour table for these.
- Game icons: one icon per settings row, stat tile or list row, from the game's `Interface\Icons`, at the left (`icon =` on the row, `S.IconBox`). One icon keeps one meaning in every module: `INV_Misc_PocketWatch_01` is time, `Spell_Nature_TimeStop` a limit or repeat, `INV_Misc_Coin_02` selling, `Trade_BlackSmithing` repairs, `Interface\Minimap\Tracking\Auctioneer` the auction house and `Interface\Minimap\Tracking\Banker` the bank (the game's own map pictures for them, not an Icons path). Spells and items show their own icon from the game by id (`GetSpellTexture`, `GetItemIcon`), never a fixed path. A module's switches that the hub also shows keep their icons in `ns.OPT_ICON` (key -> path), passed as `icon` in `Register` options. Buttons and titles get no icons.
- Check a window change without the game in `tools/preview`: `sh tools/preview/icons.sh` fetches the icons once, `lua5.1 tools/preview/shoot.lua <test folder> out.html [scene]` builds the window on fake frames from the module's `tests/<name>/wow.lua` and reports overlapping texts, and `node tools/preview/shoot.js out.html` makes a PNG. `lua5.1 tools/preview/dock.lua <test folder> out.html [scene]` builds the same window inside the hub; check both after a window change. Sample data for each window lives in `tools/preview/scenes.lua`.
- The window must work by mouse and by touch on a phone or handheld: buttons at least 28 pixels high, check boxes at least 26, no text that runs out of its row.
- Keep comments short and about intent that the code does not show.
- Do not commit release zips or `release.json`; the Release workflow makes them.

### QuestCleaner rules

- Nothing leaves the bags or the quest log without the preview. Every abandon and every delete runs from the **OK** click, for the entries the player left ticked. Never delete from a timer, an event or a slash command.
- Never offer an item a quest that stays in the log may need. When in doubt, keep it: a false "needed" only leaves an item in the bags, a false "not needed" loses it.
- A quest item that stays useful after its quest goes into `PERMANENT` in `Core.lua`, with its name in a comment, when `Data.keep` does not already have it.
- Refresh `Data.lua` with `tools/questcleaner/build_data.py` when QuestieDB releases quest fixes, and bump the version. A new field the cleaner needs goes into the generator, `ns.Data` in `AGENTS.md` and a test with small fake data (`fakeData` in `tests/questcleaner/test.lua`). Keep the generator to the standard library, and never run QuestieDB's own Lua.
- A new rule for what gets offered goes into `Core.lua` (`PlanQuests`, `PlanItems` or `ItemGoes`) with a test in `tests/questcleaner/test.lua`. `UI.lua` only shows the plan.

## Releases

`.github/workflows/release.yml` releases one folder at a time, each on its own tag, so Runeloader sees one package (`Modules.java` in the app, `module_groups` in the index):

| Folder | Tag | Zip |
|---|---|---|
| `Gulli-Toolkit` | `Core-v<version>` | `Gulli-Toolkit-<version>-forever.zip` |
| `Gulli-<Name>` | `<Name>-v<version>` | `Gulli-<Name>-<version>-forever.zip` |

1. In a pull request, bump `## Version` in the TOC of each folder you changed (`x.y.z`), and merge it.
2. Start the Release workflow on `main` from the Actions tab ("Run workflow") with `module` set to `Core` or the module name (`QuestCleaner`), once per changed folder. Or push the tag.
3. The workflow runs every test, zips that folder, writes `release.json` with the `forever` flavor, and publishes the release with both files. It refuses a tag that is already released.

After each release, the `bundle` job (`.github/workflows/bundle.yml`, `tools/bundle/build_bundle.py`) rebuilds `Gulli-Toolkit-All.zip` from the newest published release of every tag group and puts it on the fixed pre-release `bundle`. It stays a pre-release with a `release.json` that names no Forever build, so the index and the app never take it for the core. A new module needs nothing there: every `<Name>-v` group is picked up. Run **All-in-one zip** from the Actions tab to rebuild it by hand.

Never tag the core with a plain `v<version>`: the core is `Core-v…`. A tag prefix such as `release-` or `beta-` is not a module (`NOT_MODULES` in the index and the app).

The owner asks for a release after every merged bug fix and after each batch of features: bump the version and run the workflow once the pull request is merged with green CI. Runeloader shows the new version after the next nightly index run. Installing the core in Runeloader installs every module.

The tag names, asset names and `release.json` are what Runeloader and its index read. A change to them is a change in runeloader-index too.

## Language

- Write code, identifiers, comments, commit messages, issues, pull requests and these instructions in English.
- `README.md` (the toolkit) and `docs/<name>/README.md` (each module) are pages for players. It is in plain English (about B1 level): short sentences, no jargon in the main part. It keeps this order: the wordmark, a one-line pitch, features, install steps, FAQ. Technical details go inside `<details>` spoilers. Their images live next to them in `docs/<name>/` and stay small (under about 400 KB each; use JPEG for large photo-like images).
- Every addon speaks the same languages as the Runeloader app: English (the base and the fallback), Deutsch, Español, Français, Polski, Português, Русский and 中文.
  - Put no UI text in `Core.lua` or `UI.lua`. Add every new key to every language table in the addon's `Locales.lua` in the same pull request; its test fails on a missing key or a different number of placeholders.
  - Every addon always follows the game client's language (`GetLocale`), like the app follows the system language. There is no language picker (owner's decision).
  - A new language needs a table in `T`, an entry in `TAGS`, its client locales in `CLIENT` when the game has them, and a `## Notes-<locale>` line in the TOC.
  - Save a text by its key (as `item.why` does), not as a translated string.

CI runs these on every pull request to `main`. Run them before you open one:

```sh
for f in Gulli-*/*.lua tests/*/*.lua; do luac5.1 -p "$f"; done
for t in tests/*/test.lua; do lua5.1 "$t"; done
```

CI also checks that every folder has a Forever TOC that lists all its Lua files, and that every module TOC has `X-Gulli-Module` and `OptionalDeps: Gulli-Toolkit` and a `tests/<name>` folder.

The fake clients cannot show a window or run the real game rules. For a change to a module's `Core.lua` or `UI.lua`, also try it in WoW Forever: copy the folder (and `Gulli-Toolkit`) into `Interface/AddOns`, `/reload`, open it from `/gulli` and from its own slash command. For QuestCleaner and BagSpace, check the preview before **OK**, with a character whose quests and items you can lose. For Restock, check the list at a vendor before **Buy**. Attach a screenshot of a changed window to the pull request. Say what you checked, on which client and device, and report any check you could not run.
